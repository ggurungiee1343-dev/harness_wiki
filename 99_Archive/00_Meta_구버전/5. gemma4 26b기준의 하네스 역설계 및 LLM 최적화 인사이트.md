# Gemma4 26B 기준의 하네스 역설계 및 LLM 최적화 인사이트

> **생성 일시**: 2026-05-26
> **성격**: DeepSeek v4 Flash 기준으로 작성된 기존 제안들을 **Gemma4 26B (로컬 llama-server, 32K context)** 관점에서 재평가
> **핵심 원칙**: "가장 약한 모델(=Gemma4)이 이해할 수 있는 문서 = 모든 모델이 이해하는 문서"
> **참조**: `하네스_역설계_및_LLM_최적화_인사이트.md` (DeepSeek 기준 원본)

## 📋 차이 요약: DeepSeek vs Gemma4

| 특성 | DeepSeek v4 Flash | Gemma4 26B |
|------|-------------------|------------|
| Context 길이 | 128K | 32K (1/4) |
| 문서 간 추론 (크로스-레퍼런스) | 강함 — "ADR 문서 보고 판단해" 가능 | 약함 — 단일 문서 선호 |
| 긴 문서 이해 | 우수 — 593줄 장애 기록 전체 파악 | 중간 — 상단 핵심 놓침 위험 |
| 자연어 모호성 처리 | 유연 — "00_Meta 리스트 보여줘" OK | 취약 — 엉뚱한 방향으로 감 |
| 오픈엔드 추론 | 자연스러움 | 정형화된 입력에 더 강함 |

## 🎯 Gemma4 기준 최적화 제안 (5항목)

### ① (최우선) 문서 구조 단순화 — 크로스 레퍼런스 제거

**DeepSeek 기준:** "ADR 문서 보고 판단해" 가능 → 문서 간 연결 자연스러움
**Gemma4 기준:** 다른 문서 찾으러 가는 걸 기대하면 안 됨

| 전환 방향 | DeepSeek 방식 | Gemma4 방식 |
|-----------|--------------|-------------|
| 참조 방식 | `§2 참조`, `→ system_monitor.py` | **실제 규칙/내용을 그대로 중복 기재** |
| 문서 구조 | 분산된 여러 문서에 핵심 분산 | **각 문서가 자기 완결적** |
| 효과 | 문서 간 연결로 context 절약 | Gemma4가 한 문서만 읽어도 모든 규칙 파악 |

**예시:**
- ❌ `constitution.local.md`: "HERMES.md §3 참조"
- ✅ `constitution.local.md`: "HERMES.md §3: 모든 .pys 파일은 snake_case .py로 변경" (실제 규칙 직접 기재)

> **이 항목이 Gemma4에게 가장 큰 효과를 줌.** 다른 건 다 제쳐두고 이거 하나만 적용해도 Gemma4 정확도가 확 올라감.

---

### ② 명령어 기반 정형화된 워크플로우

**DeepSeek 기준:** "00_Meta 파일 리스트 알려줘" 자연어 OK
**Gemma4 기준:** 자연어 모호하면 엉뚱한 방향으로 감

| 방식 | DeepSeek | Gemma4 |
|------|----------|--------|
| 파일 요청 | `"meta 폴더 리스트 보여줘"` | **`/list 00_Meta`** |
| 상태 확인 | `"봇 상태 어때?"` | **`/status`** (정형화된 출력) |
| 진단 | `"왜 안 되지?"` | **`/diag`** (고정 포맷 출력) |

Gemma4는 **일관된 입력 → 일관된 출력** 패턴에서 훨씬 잘 동작. 자연어 자유도는 DeepSeek에 맡기고, Gemma4는 구조화된 명령어를 받는 쪽으로 역할 분담.

---

### ③ 단일 파일 진단 스크립트 (헬스체크 대체)

**DeepSeek 기준:** 여러 로그 파일 크로스 분석 가능 → 각종 로그를 뒤져서 원인 추론
**Gemma4 기준:** 로그 파일 여러 개 읽으면 context 부족 + 추론 약함

→ 하나의 스크립트가 모든 시스템 상태를 수집해서 **하나의 정형화된 출력**으로
→ Gemma4가 그 출력 하나만 읽으면 전체 파악 가능

```
# system_status 예시 출력 포맷
PROCESS:hermes1=RUNNING(pid=12345)|hermes2=RUNNING(pid=12346)|gateway=STOPPED
PORT:8005=LISTEN|8080=LISTEN
DISK:/=65%|/tmp=12%
MEMORY:free=8GB|llama=6.2GB
LOG:last_error=none|uptime=72h
```

**핵심:** 한 줄 한 줄이 atomic한 `KEY=VALUE`면 Gemma4가 처리하기 쉬움. 에이전틱 루프에서 이 출력을 보고 "gateway=STOPPED" 발견 → 조치 가능.

---

### ④ 결정 메모 (가벼운 ADR)

**DeepSeek 기준:** "왜 이렇게 했는지" 문서 간 연결해서 추론 가능
**Gemma4 기준:** 추론 못 함. 명시적으로 알려줘야 함.

→ `hot.md` 또는 `시스템 상태.md`에 **1줄 결정 메모**만 추가

```
#008: Gateway 충돌 → Bot→llama-server 직결 우회
  이유: Gateway가 Telegram 토큰 충돌로 폴링 불가

#016: DummyRouter 전파 → lazy import로 해결
  이유: from X import Y가 import 시점 값을 복사
```

Gemma4가 "왜 이렇게 되어있지?" 하고 추론하는 토큰 낭비를 막고, 바로 다음 단계로 넘어갈 수 있게 함.

---

### ⑤ DeepSeek 원 제안 대비 판단 변화

| 원래 제안 (DeepSeek 기준) | Gemma4 기준 재평가 | 이유 |
|-------------------------|-------------------|------|
| 단위 테스트 인프라 | **유지 (但, 역할 축소)** | 테스트 자체는 필요. 하지만 Gemma4가 테스트 코드를 작성/분석하는 건 기대 어려움. 미리 작성된 테스트만 실행하는 용도 |
| Git Workflow (feature branch) | **우선순위 하향** | Gemma4가 Git 브랜치 전략을 이해하고 따르는 건 과부하. 나중에 DeepSeek 전용 작업으로 |
| 모듈 헬스체크 (+/health) | **③ 단일 진단 스크립트로 대체** | 여러 모듈 각각 체크하는 건 context 낭비. 하나의 통합 스크립트가 더 효율적 |
| ADR (전문 문서) | **④ 결정 메모로 간소화** | Gemma4에게 긴 ADR 문서 읽히는 건 비효율. 1줄 결정 메모면 충분 |

## 💡 핵심 인사이트

1. **Gemma4 최적화 = 시스템 전체 최적화:** 가장 약한 모델 기준으로 맞추면 모든 모델이 수혜
2. **문서 자급자족이 제일 중요:** 크로스 레퍼런스 제거만으로 Gemma4 정확도 급상승
3. **정형화된 입출력이 열쇠:** 자연어 자유도는 DeepSeek에, 구조화된 명령어는 Gemma4에
4. **결정 근거를 명시하라:** "왜?"라는 추론을 Gemma4에게 요구하지 말고, 문서에 직접 적어라
5. **역할 분담이 답:** DeepSeek = 추론/분석/자연어, Gemma4 = 정형화된 작업/빠른 응답
