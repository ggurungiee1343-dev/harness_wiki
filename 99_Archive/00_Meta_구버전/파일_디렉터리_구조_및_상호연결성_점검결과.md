### 🔄 핵심 상호 연결 흐름 (Interaction Flows)

1. **텔레그램 명령어 인터페이스**
   - `hermes_local.py`가 `Application.run_polling()`으로 PTB v22 기동 → 텔레그램 메시지 수신
   - `post_init`에서 인라인 키보드 전송, 모든 핸들러 등록 (9개 서브모듈)
   - PTB v22 `run_polling()`은 원래 절대 리턴하지 않지만 → Zombie Poller 패치로 `updater.running` 모니터링 + `sys.exit(0)` → launchd KeepAlive 자동 재시작 (아래 4절 상세)

2. **3-way LLM 라우팅 (HybridRouter → _call_primary_with_fallback)**
   - `harness_agent.get_llm_response()` → `hybrid_router.route_and_execute(force_primary=mode)`
   - `_call_primary_with_fallback(messages, force_primary)` — 모드 파일(`llm_mode.txt`) 기반:
     - **1차 시도**: `_call_local()` — Gemma4 (llama-server) `completions.create()` + 수동 `<start_of_turn>` 포맷 (chat template 버그 우회)
     - **2차 시도**: `_call_deepseek()` — DeepSeek API `chat.completions.create()`
     - **3차 시도**: `_call_nvidia()` — NVIDIA NIM 70B `chat.completions.create()`
   - `_FALLBACK_ORDER` = [`_call_deepseek`, `_call_nvidia`, `_call_local`] — 자동 폴백 체인
   - 자동 폴백 시 `llm_fallback.txt` 기록 → `/status` 명령어에서 표시

3. **파일 기반 모드 공유**
   - `~/.hermes/llm_mode.txt` — Gemma4 / DeepSeek / NVIDIA 70B 3-way 선택
   - `hermes_local.py`와 `harness_agent.py`가 동일 파일을 읽어 상태 공유 — 프로세스 간 IPC
   - `/model Gemma4`, `/model DeepSeek`, `/model NVIDIA` 명령어로 전환

4. **LLM 응답 → 핸들러 체인**
   - `_call_llm()` → `get_llm_response()` → 응답 문자열 반환 → `add_to_history()` → 텔레그램 채팅 전송
   - Dreaming 모드: `execute_dreaming_job()` → 서브프로세스 분리, 결과 취합 후 전송

5. **IngestEngine 자동 분류**
   - `cmd_ingest` → `ingest_engine.py` → Clippings 파일 분석 → `llm_func`(`get_llm_response`)로 분류 → 적절한 wiki/ 디렉터리로 이관

## 🐛 4. 구조적 결함 3종 (2026-05-27 발견, 수정 완료)

### 🔴 결함 #1: Zombie Poller — `run_polling()` 절대 리턴 문제

**증상:** PTB v22의 `run_polling()`은 내부적으로 `loop.run_forever()`를 호출하여 절대 리턴하지 않음. 장애/중단 시 프로세스가 좀비 상태로 남거나, launchd가 재시작을 감지하지 못함.

**영향:** 크리티컬. 장애 복구 불가, 프로세스 누적, 메모리 고갈.

**근본 원인:** PTB v22 아키텍처: `run_polling()` → `_start_polling()` → `loop.run_forever()`로 무한 루프 진입. `sys.exit()` 호출이 없으면 프로세스가 종료되지 않음.

**수정 사항:**
- `hermes_local.py` 내 `run_polling()` 호출부에 직접 `updater.running` 상태 모니터링 루프 추가
- 루프 중단/예외 발생 시 `sys.exit(0)` 호출 → launchd의 KeepAlive가 프로세스를 자동 재시작
- polling watchdog 15초 주기 + `bot.get_me()` 60초 체크로 무반응 상태 감지

```python
# 수정된 패턴 (hermes_local.py):
try:
    app.run_polling()
except Exception:
    sys.exit(0)  # → launchd KeepAlive 재시작
```

### 🔴 결함 #2: 에러 침묵 — 3중 차단으로 모든 예외 무시

**증상:** asyncio 관련 WARNING 레벨 예외 + bare `except: pass` 2곳 + `PYTHONUNBUFFERED` 미설정 → 3중 장벽으로 모든 예외가 침묵함. 장애가 로그에 기록되지 않음.

**영향:** 하이. 진단 불가능 상태, 장애 발생 시 원인 파악 불가.

**근본 원인 (3중 차단):**
1. **Asyncio WARNING 레벨:** `asyncio.get_event_loop().set_exception_handler()` 미등록 → 기본 핸들러가 WARNING 레벨로만 출력, STDOUT 버퍼링으로 사라짐
2. **Bare `except: pass`:** `_system.py` 등에서 최소 2곳의 예외를 무시하는 `except: pass` 패턴
3. **`PYTHONUNBUFFERED` 미설정:** 로그가 버퍼링되어 launchd 로그에 기록되지 않고 유실

**수정 사항:**
- `PYTHONUNBUFFERED=1` launchd plist에 추가, `python3 -u` 플래그 사용
- Asyncio 글로벌 예외 핸들러 등록 (ERROR 레벨 로깅)
- BARE `except: pass` 2곳을 `except Exception as e: logger.error(...)`로 교체
- `Plists/` 디렉터리에 백업 보관

### 🔴 결함 #3: Gemma4 Chat Template — GGUF 내장 Jinja 템플릿 파손

**증상:** `chat.completions.create()` 호출 시 GGUF에 내장된 Jinja2 chat template이 깨져서 빈 문자열("")을 반환. 모든 LLM 응답이 공백으로 표시됨.

**영향:** 크리티컬. Gemma4 모드 사용 불가.

**근본 원인:** Gemma4 GGUF (gemma-4-26B-A4B-it-UD-Q4_K_S.gguf) 내 `tokenizer.chat_template`의 Jinja 변환 버그. 특히 시스템 프롬프트가 포함된 다중 턴 메시지에서 template 파싱 실패.

**수정 사항:**
- `chat.completions.create()` → `completions.create()`로 전환 (template bypass)
- 수동 `<start_of_turn>` 포맷 적용:

```python
# _call_local() in harness_agent.py:
```
