* **조치**: Plist 파일 내 병렬 슬롯 수를 `-np 1`로 축소 조정하고 서비스를 재기동 완료. 슬롯당 65,536 컨텍스트를 온전히 확보하여 서버 수준에서의 강제 기억 상실 원인을 완벽히 예방 및 해결함.

* **문제 인식**: L2 episodic_memory.json이 1.7MB / 83건으로 급증했으나, L3 패턴 학습이 Early Exit(rows=0)에 걸려 정체된 상태가 지속됨. 용량 기준 강제 증류가 없어 메모리 블로트 리스크 존재.

## 🚨 [결함해소] 결함 #1: Zombie Poller / 봇 이중 기동 — PID 파일 자동 교체 방식으로 근본 해결 (2026-06-11)
- **증상**: launchd가 봇을 재시작할 때 구 프로세스가 완전히 종료되기 전에 신규 프로세스가 기동 → 이중 실행 → "다른 인스턴스가 이미 실행 중" 메시지 후 신규 프로세스 자체 종료 → 봇 무응답
- **원인**: `fcntl.flock(LOCK_EX | LOCK_NB)` 방식은 launchd의 즉시 재시작 타이밍 경쟁 조건에서 신규 프로세스가 락을 획득하지 못하고 종료되는 경우 발생
- **해결**: `hermes_local.py` — `_ensure_single_instance()` 신규 함수
  - PID 파일(`~/.hermes/hermes_local.pid`) 기반으로 구 프로세스 직접 종료 후 교체
  - SIGTERM → 5초 대기 → 미종료 시 SIGKILL → 신규 인스턴스 기동
- **재발 방지**: 어떤 재시작 시나리오에서도 신규 인스턴스가 구 인스턴스를 밀어내고 단독 실행 보장

## 2026-06-12 버그 수정 및 재발방지

### BUG-001: episodic_memory.json 2.3MB 비대 (임베딩 인라인 저장)

**현상**: `episodic_memory.json`이 2.3MB+ 로 비대화. L2 로드/저장 속도 저하.  
**근본 원인**: `_promote_to_l2()`에서 384차원 float 배열(`embedding`)을 JSON 인라인으로 직렬화. 에피소드 200개 × ~3KB = 600KB+.  
**수정**: 인라인 `"embedding"` 필드 제거. turbovec `.npy` 외부 인덱스에만 저장. 기동 시 `_strip_inline_embeddings()`로 기존 파일 자동 마이그레이션.  
**재발방지**: `_promote_to_l2()`에 `# NO inline embedding — turbovec only` 주석 유지.

### BUG-002: L2 eviction `if` → `while` (1개만 제거하는 버그)

**현상**: L2가 용량 초과여도 재기동 후 1개만 evict되고 루프 종료.  
**근본 원인**: `if len(episodes) > L2_MAX_SIZE or ...` — `if`문으로 단 1회만 실행.  
**수정**: `while`로 변경 + `_get_l2_bytes()` 기반 실제 직렬화 크기 체크.  
**재발방지**: 용량 제한 로직은 반드시 `while` 사용.

### BUG-003: Model Collapse — LLM 응답 L2 자동 승격

**현상**: `assistant` 역할 발화가 MID 키워드를 포함하면 점수 3.0+으로 L2에 승격됨. LLM이 자기 응답을 다시 컨텍스트로 받아 다양성 붕괴.  
**근본 원인**: `ImportanceScorer.score()`에 role 기반 상한이 없었음.  
**수정**: `if role == "assistant": result = min(result, L1_TO_L2_THRESHOLD - 0.1)`  
**재발방지**: ImportanceScorer는 user 발화만 L2 후보로 삼아야 함. 논문: Model Collapse (2305.17493).

### BUG-005 (2026-06-17): Hermes1 봇 행·크래시 루프 3종 복합 장애

**현상**: 텔레그램 봇 무응답(3시간 30분), 이후 재시작해도 PID가 5~15초마다 계속 바뀌는 크래시 루프

**근본 원인 3가지 (순서대로 발생)**
1. 네트워크 단절(`httpx.ReadError`) 후 PTB 내부 폴링 루프가 죽지도 않고 멈힘(행). launchd `KeepAlive`는 프로세스 종료시에만 재시작해 무력화
2. 워치독 `kill -9`로 강제종료 → 텔레그램 서버측 getUpdates long-poll 연결이 잔류 → 5초 뒤 재시작된 새 프로세스가 즉시 `telegram.error.Conflict: terminated by other getUpdates request`로 사망 → `ThrottleInterval=5` 재시작 반복
3. `hermes_local.py:483`의 `except Exception: pass`가 폴링 종료 예외를 완전히 삼켜 진짜 원인 불명(3시간 이상 헛된 디버깅)

**수정**
- `hermes_local.py`: `except Exception: pass` → `logger.error(f"[Polling 종료 원인] {type(e).__name__}: {e}")` — 진단 가능하도록
- `hermes_local.py`: 폴링 루프에 `_HEARTBEAT.touch()` 추가(15초마다) — 워치독이 메시지 없는 조용한 상태와 행 상태를 구분 가능
- `check_bot_alive.sh`: SIGTERM 우선(최대 5초 대기) → 그래도 살아있으면 SIGKILL fallback. kickstart 전 5초 대기
- `check_bot_alive.sh`: 로그 mtime → 하트비트 파일 mtime 기준으로 변경(3분 임계값). 텔레그램 알람 제거

**재발방지**
- 향후 "텔레그램 안 됨" 신고 시 가장 먼저 `curl --max-time 6 https://api.telegram.org` 네트워크 확인
- 워치독 재시작 시 반드시 SIGTERM 우선 — SIGKILL은 Conflict 루프 유발
- ISP 차단/네트워크 문제인 경우 공유기 재부팅으로 해결 가능(2026-06-17 실제 확인)
