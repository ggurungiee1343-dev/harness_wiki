## 1. Self-Correction Loops 아티클 3제안 — 내 시스템 적용 분석

> 출처: Self-Correction Loops (Anthropic Fable 5 실험) 아티클 2026-06

아티클이 제안하는 3가지 핵심 개념과 MJ 시스템 현황입니다.

### 제안 1 — 외부 독립 Verifier (자기비판 ≠ 채점)

**아티클 주장**: 모델이 자신의 출력을 스스로 평가하는 것은 의외로 약하다. 별도의 Verifier가 독립적인 맥락에서 채점할 때 훨씬 더 잘 움직인다.

| 항목 | 내용 |
|---|---|
| **MJ 시스템 적용 현황** | ✅ `modules/proposal_validator.py` — held-in + held-out 체크리스트로 외부 기준 제공 |
| **장점** | 수정 전에 "이미 알려진 실패"와 "깨지면 안 되는 케이스" 두 가지를 동시에 체크. 감정 없이 기계적 채점 |
| **단점 1** | Verifier 자체가 아직 자동 실행이 아님. 수동으로 `pre_check()` 호출해야 함 |
| **단점 개선안** | `PreToolUse` 훅에 연결: `handlers/*.py` 파일 Edit 시 자동으로 `pre_check()` 호출 후 체크리스트를 Claude 컨텍스트에 주입 |
| **단점 2** | held-out 케이스가 하드코딩(`HANDLER_FUNCTIONS` 딕셔너리). 실제 정상 동작 케이스가 자동 수집되지 않음 |
| **단점 개선안** | `/test` 명령어로 각 핸들러 smoke test 결과를 weakness.db에 "success" 기록 → held-out 케이스 자동 갱신 |

---

### 제안 2 — Memory Across Sessions (5단계 기억 구조)

**아티클 주장**: Fable 5만이 5단계 전체를 밟았다. Sonnet은 1단계(Fail 문서화)에서 멈추고, Opus는 3단계(Verify)까지 가지만 검증률이 낮다.

```
1. Fail      → 실패를 문서화
2. Investigate → 왜 실패했는지 파악
3. Verify    → 진단을 검증된 사실로 전환
4. Distill   → 검증된 내용을 일반적인 규칙으로 압축
5. Consult   → 다음번에는 규칙을 읽고 활용
```

| 단계 | MJ 시스템 대응 구조 | 현황 |
|---|---|---|
| **Fail** | `weakness_miner.record_failure()` → `weakness.db` | ✅ 자동 기록 |
| **Investigate** | `WeaknessMiner._make_signature()` 에러 패턴 추출 | ✅ 자동 (정규식 클러스터링) |
| **Verify** | 3회 반복 시 텔레그램 알림 → 사람이 확인 | ⚠️ 반자동 (사람 확인 필요) |
| **Distill** | 에러보고서 자동 append + CLAUDE.md 수동 반영 | ⚠️ 반자동 |
| **Consult** | 다음 세션 SessionStart Hook이 05_시스템 상태.md 주입 | ✅ 자동 |

**장점**: 5단계 중 1·2·5단계는 완전 자동. 전체 흐름 구조는 갖춰짐.

**단점**: 3·4단계(Verify→Distill)가 아직 수동 개입 필요. "진단이 맞는지 검증" 로직 없음.

**단점 개선안**: `ProposalValidator.record_result()` 호출 시 `held_in_ok=True`인 경우 → 자동으로 `CLAUDE.md`에 "이 패턴은 해결됨" 규칙 append하는 `distill_to_memory()` 함수 추가. (3→4단계 자동화)

---

### 제안 3 — Loop Engineering (목표와 기억의 구조 설계)

**아티클 주장**: 중요한 것은 두 가지. (1) Verification은 여전히 외부에서. (2) Memory는 디스크에 있어야지 컨텍스트 안에만 있으면 안 된다.

| 원칙 | MJ 시스템 구현 | 현황 |
|---|---|---|
| **Verification 외부** | ProposalValidator (독립 held-in/held-out) | ✅ |
| **Memory 디스크** | weakness.db / proposal_validation.db / wiki git / Scripts git | ✅ |
| **목표 구조 설계** | CLAUDE.md → 세션 규칙 / 01_hot.md → 현재 목표 / 05_시스템 상태.md → 이력 | ✅ |

**장점**: "모델은 잊지만 기록은 잊히지 않는다" 원칙이 현재 5개 디스크 저장소(wiki.git / scripts.git / weakness.db / proposal_validation.db / 에러보고서.md)로 구현됨.

**단점**: 기억 구조가 파일·DB에 나뉘어 있어 "전체 패턴을 종합해서 보는" 대시보드가 없음.

**단점 개선안**: 월간 `/harness_report` 명령어 — weakness.db + proposal_validation.db + git log를 한 페이지로 요약 → 텔레그램 전송. (구현 용이, 효과 높음)

## 5. L3 — Hooks (3개 자동화)

### Hook 1 — SessionStart (세션 시작 컨텍스트 주입)

**동작 흐름**:
```
Claude Code 새 세션 열기
    ↓ (자동, ~1초)
wiki/00_Meta/session_start_hook.sh 실행
    ↓
01_hot.md → 최근 ## 섹션 3개 (800자 캡)
05_시스템 상태.md → 최신 ## 2026 섹션 (400자 캡)
    ↓
Claude 컨텍스트에 "=== 세션 시작 컨텍스트 ===" 자동 주입
    ↓
새 세션에서 "어디까지 했지?" 질문 불필요
```

**v2 개선점**: 2591자 → 1297자 (50% 감소). 최근 3섹션만 추출.

**관리**:
```bash
# 훅 스크립트 위치
~/Applications/Mjobsidian/wiki/00_Meta/session_start_hook.sh

# 테스트
echo '{}' | bash ~/Applications/Mjobsidian/wiki/00_Meta/session_start_hook.sh
```

**컨텍스트를 최신 상태로 유지하는 방법**: `01_hot.md`에 현재 작업을 잘 기록. 훅이 자동으로 읽어 주입.

---

### Hook 2 — PostToolUse (Wiki 자동 스테이징)

**동작 흐름**:
```
Claude Code에서 wiki 경로 파일 수정 (Write/Edit)
    ↓ (자동, ~0.5초)
wiki_autostage.py 실행
    ↓
git -C wiki add <수정된 파일>
    ↓
커밋은 수동 (Stop Hook에서 안내)
```

**대상 경로**: `~/Applications/Mjobsidian/wiki/` 하위 모든 파일

**Scripts 파일은 자동 스테이징 안 됨** → 수동 커밋 필요:
```bash
git -C ~/Applications/Mjauto/Scripts add -A
git -C ~/Applications/Mjauto/Scripts commit -m "feat: 변경 내용"
```

---

### Hook 3 — Stop (세션 종료 체크리스트)

**동작 흐름**:
```
Claude Code 세션 종료 (또는 /clear)
    ↓ (자동)
stop_hook.py v2 실행
    ↓
최근 30분 내 수정된 handlers/*.py, modules/*.py 스캔
    ↓
변경 없음? → "✅ 세션 종료 — 파일 변경 없음" 간단 메시지
변경 있음? → 수정 파일 목록 + 메타 업데이트 안내
```

**v2 개선점**: 이전엔 탐색만 해도 동일 체크리스트 표시(false-positive). 이제 실제 파일 수정 세션에서만 상세 안내.

**안내 조건별 메타 업데이트 대상**:
| 조건 | 업데이트 파일 |
|---|---|
| modules/ 파일 변경 | 05_시스템 상태.md + 02_스크립트 정보.md |
| handlers/ 파일만 변경 | 05_시스템 상태.md |
| wiki 미커밋 있음 | `git -C wiki commit` |

---

### Hook 설정 파일
```json
// ~/.claude/settings.json
{
  "hooks": {
    "SessionStart": [{"hooks": [{"type": "command", "command": "bash '~/...session_start_hook.sh'"}]}],
    "PostToolUse": [{"matcher": "Write|Edit", "hooks": [{"type": "command", "command": "python3 '~/...wiki_autostage.py'"}]}],
    "Stop": [{"hooks": [{"type": "command", "command": "python3 '~/...stop_hook.py'"}]}]
  }
}
```

## 6. L4 — Sub-Agents (전담 에이전트)

### Agent 1 — meta-updater

**용도**: 메타 7종 자동 업데이트 전담. 코드 수정 후 "메타 업데이트해줘" 한 마디면 실행.

**동작**:
1. 현재 세션 작업 분석 (git status, 수정 파일 목록)
2. 변경 유형 판단 (신규 모듈 / 버그 수정 / 구조 변경 등)

## 8. Self-Harness 3단계 루프

> Shanghai AI Lab Self-Harness 논문 구현. 수정이 개선인지 회귀인지 자동 판단.

### 단계 1 — Weakness Mining (`modules/weakness_miner.py`)

**역할**: 텔레그램 핸들러 에러를 자동 수집·클러스터링.

**동작**:
```python
# 핸들러 except 블록에서 자동 호출
await get_weakness_miner().record_failure("cmd_scan", str(e))
    ↓
weakness.db에 (action, error_signature, timestamp) 기록
    ↓
동일 패턴 3회↑ (최근 7일) → 텔레그램 알림 + 에러보고서 append
```

**현재 모니터링 대상** (6핸들러 14포인트):
| 핸들러 파일 | 모니터링 명령어 |
|---|---|
| `handlers/_stock.py` | cmd_stock, cmd_scan, cmd_chart |
| `handlers/_vault.py` | cmd_vault_duplicates, cmd_vault_graph |
| `handlers/_file.py` | cmd_web, cmd_recent |
| `handlers/_system.py` | cmd_exec, cmd_status, cmd_audit |
| `handlers/_grill.py` | cmd_grill |
| `handlers/_research.py` | cmd_research_local |

**텔레그램 알림 예시**:
```
⚠️ [Weakness Mining] 반복 실패 감지
━━━━━━━━━━━━━━━━━━
📍 명령어: cmd_scan
🔁 반복 횟수: 3회 (7일 내)
❌ 패턴: KeyError:'ema200'
🔧 수정 대상: handlers/_stock.py
```

**누적 데이터 조회**:
```bash
cd ~/Applications/Mjauto/Scripts
python3 -c "
from modules.weakness_miner import get_weakness_miner
for r in get_weakness_miner().get_top_failures(days=30):
    print(f'{r[\"action\"]:20} {r[\"count\"]:3}회  {r[\"signature\"]}')
"
```

**데이터 위치**: `~/.hermes/runtime/weakness.db`

### 단계 2 — Harness Proposal

수동 단계. WeaknessMiner 알림을 받으면:
1. Claude Code에 해당 파일 점검 요청
2. 최소 수정안 작성
3. Proposal Validation 실행 후 적용

---

### 단계 3 — Proposal Validation (`modules/proposal_validator.py`)

**역할**: 수정 전 체크리스트 자동 생성. held-in + held-out 두 기준 동시 검증.

**수정 전 호출**:
```python
from modules.proposal_validator import get_validator

checklist = get_validator().pre_check(
    "handlers/_stock.py",
    "cmd_scan KeyError 수정"
)
print(checklist)
```

**출력 예시**:
```
🔍 Proposal Validation 체크리스트
━━━━━━━━━━━━━━━━━━━━━━━━━━━━
📁 수정 대상: handlers/_stock.py
📝 수정 내용: cmd_scan KeyError 수정

【Held-in: 알려진 실패 케이스 — 수정 후 반드시 해결돼야 함】
  ❌ cmd_scan: KeyError:'ema200' (3회)

【Held-out: 정상 동작 케이스 — 수정 후 깨지면 안 됨】
  ✓ cmd_stock(TICKER)
  ✓ cmd_scan()
  ✓ 차트 분석

【승인 기준】
  → held-in 개선 AND held-out 유지 시 승인
  → 하나라도 나빠지면 거부
```

**수정 후 결과 기록**:
```python
get_validator().record_result(
    "handlers/_stock.py",
    passed=True,
    detail="KeyError 해결, 기존 케이스 통과"
)
```

**거부 시**: `06_에이전트_오류_및_재발방지_보고서.md`에 자동 기록

**이력 조회**:
```python
for r in get_validator().get_history(last_n=10):
    print(r)
```

**데이터 위치**: `~/.hermes/runtime/proposal_validation.db`
