### BUG-MJS-016: KR 종목코드 앞자리 0 소실

### BUG-MJS-018: 차트 조회 subprocess 동기 호출 → 콜백 타임아웃
**증상**: 버튼 눌러도 반응 없음, `telegram.error.BadRequest: Query is too old and response timeout expired`.

**수정**: 동일 스레드 분리 패턴 적용 — `asyncio.wait_for(loop.run_in_executor(...))`.

### BUG-MJS-021 (자기귀책): batch_id 타임스탬프 형식 → 콜백 데이터 64바이트 초과
**증상**: 실제 프로덕션(auto_scan_morning.py, 2026-07-03 21:06~23:28 실행분)에서 "초우량(KR)" 버튼 클릭 시 무반응, `telegram.error.BadRequest: Button_data_invalid`.
**원인**: BUG-MJS-020 수정 시 batch_id를 `YYYYMMDD_HHMMSS`(15자) 전체 타임스탬프로 만들어 `mjstock_chart:{ticker}:{screener_key}:{date_str}:{batch_id}` 조합이 검색기 키가 긴 경우(`chowuryang_kr`, `nongsa_danta_kr` 등) 66바이트가 되어 텔레그램 콜백 데이터 64바이트 한도 초과.

batch_id = format(int(datetime.now().timestamp() * 1000) & 0xFFFFFFFF, "08x")

## [2026-07-03] BUG-010: 나스닥500 아침 스캔 "스캔 실패" — cron ulimit(FD 256개) 고갈

**증상**: `MJstock 미국(나스닥500) 아침 스캔` 텔레그램 메시지에서 우량주농사·세력주농사·초우량주 3개 검색식이 `❌ 스캔 실패`로 표시. 로그(`logs/scan_morning.log`)에는 서로 다른 무관한 티커마다 "possibly delisted", "unable to open database file" 에러가 여러 날에 걸쳐 반복 등장 — 얼핏 개별 티커 문제처럼 보이나 실제로는 아님.

**원인**: cron으로 실행되는 프로세스는 macOS 기본 `ulimit -n 256`(launchd 기본값)을 그대로 상속. `run_scan.py`가 나스닥100(top-n 500) 전체를 순회하며 yfinance 실패 시 KIS API로 폴백하는데, 이 과정에서 실패한 HTTP 커넥션이 파일 디스크립터를 계속 점유 → 스캔 후반부(400번째 티커 이후)에 256개 한도 초과 → `save_scan_result()`의 `matched.to_csv()` 호출 시점에 `OSError: [Errno 24] Too many open files`로 전체 프로세스 크래시(rc=1). `run_scan.py` 내부 per-ticker 예외처리(`try/except: continue`)는 정상 동작하지만, FD 고갈은 그 예외처리 범위 밖(pandas to_csv, sqlite 연결 등)에서 터지므로 못 잡힘. 로그에 남는 "delisted"/"unable to open database file" 메시지들은 `result.stderr[:400]` 잘림 때문에 보이는 지엽적 증상이고, 실제 크래시 원인(traceback)은 이 400자 제한에 잘려 로그에 안 남음.

**재현**: `ulimit -n 256; python run_scan.py --screen uryangju --universe nasdaq100 --top-n 500` → 동일 traceback 재현. 인터랙티브 셸(ulimit 기본 높음)에서는 동일 커맨드가 정상 완료됨 — 즉 코드 버그가 아니라 cron 환경 고유의 제약.

**수정 (2026-07-03)**: crontab의 아침/미국장중/한국장중 3개 스캔 라인에 `ulimit -n 4096;` 프리픽스 추가.
```
0 7 * * 1-5 ulimit -n 4096; cd /Users/bluesea/Applications/Mjstock && .venv/bin/python auto_scan_morning.py ...
```

**재발방지**:
- "스캔 실패" 발생 시 개별 티커 delisted 에러로 오진단하지 말 것 — 여러 날에 걸쳐 서로 다른 티커에서 반복되면 FD 고갈 의심
- `result.stderr[:400]` 잘림으로 인해 로그만으로는 진짜 원인 추적 불가 — 재현이 필요하면 반드시 `ulimit -n 256`으로 강제 재현할 것
- **Claude Code 셸(샌드박스)에서는 crontab 쓰기가 반영 안 됨**: `crontab -` 실행 시 root 소유 프로세스로 멈추고 exit 0을 반환하지만 `crontab -l` 재확인 시 변경 없음 (2026-06-30 최초 발견 당시엔 "타임아웃"으로 기록했으나, 실제로는 좀비 프로세스로 멈추고 거짓 성공을 리턴하는 패턴). crontab 수정은 항상 사용자가 Terminal.app에서 직접 실행해야 함 — Claude가 재시도해도 결과 동일.

### D. Llama-Server 멀티 슬롯 정합성 교정 (2026-06-05 추가 조치)

- **새로운 업데이트**: `~/.hermes/config.yaml`와 `~/Applications/venu/.hermes2/config.yaml`에 전체 toolsets를 포함하도록 2026-06-06에 적용되었습니다. 이제 두 Hermes 인스턴스 모두 모든 도구를 사용할 수 있습니다.
* **문제점**: 대화 세션이 다소 길어지면 에이전트가 본인이 방금 전까지 하던 작업 내역이나 생성한 파일들의 존재 자체를 잊어버려, "파일이 존재하지 않는다"며 추측성/환각 답변을 하는 기술적 한계 발생.
* **원인**: `com.bluesea.llama_server2.plist` 서비스가 `-np 2`로 구동되어 65,536 컨텍스트를 슬롯당 32,768토큰으로 쪼개고 있었음. Hermes 설정(`context_length: 65536`)에 맞춰 32k가 넘는 긴 메시지를 전송했을 때, Llama 서버단에서 대화 앞부분의 기억(파일 생성 내역 등)을 예고 없이 강제 Truncation(잘림) 처리하여 기억을 유실시킴. SWA 캐시 무효화로 인한 성능 저하도 동반됨.
* **조치**: Plist 파일 내 병렬 슬롯 수를 `-np 1`로 축소 조정하고 서비스를 재기동 완료. 슬롯당 65,536 컨텍스트를 온전히 확보하여 서버 수준에서의 강제 기억 상실 원인을 완벽히 예방 및 해결함.

### E. Bio-Memory Engine v9.3 — L2 메모리 블로트 리스크 대응 강제 증류 도입 (2026-06-05 추가 조치)

* **문제 인식**: L2 episodic_memory.json이 1.7MB / 83건으로 급증했으나, L3 패턴 학습이 Early Exit(rows=0)에 걸려 정체된 상태가 지속됨. 용량 기준 강제 증류가 없어 메모리 블로트 리스크 존재.
* **원인**: dreaming_v2.py의 L3 패턴 학습이 L2 증류 결과(rows)에만 의존했고, 용량 기준 체크가 없어 L2가 계속 팽창해도 강제 전이가 발생하지 않음.
* **조치 1 — bio_memory_engine.py**: `_get_l2_bytes()` 메서드 추가로 실시간 KB/MB 확인 가능. `get_memory_status()`에 바이트 정보 포함.
* **조치 2 — dreamer_layer.py**: `offline_consolidation_forced()` 추가 — 중요도 하위 50%를 조건 없이 강제 L3 전이. 용량 위기 시 자동 발동.
* **조치 3 — dreaming_v2.py**: `_run_offline_consolidation()`에 용량 위기(rows > 80 or bytes > 900KB) 탐지 로직 추가 → 강제 증류 호출. `_commit_to_l3_semantic()` atomic write 적용.
* **기대 효과**: L2가 1MB를 넘으면 중요도 무관 강제 증류로 L3 패턴 학습이 지속되며, write 중 crash에도 데이터 유실 없음.

### BUG-MJS-013: `app.py` 스캔 큐 1초 폴링 리런 — 화면 깜빡임 + 차트 탭 표시 불일치

### BUG-MEMREF-001: `memory_refinement.py` 에빙하우스 공식 중복 구현 (불일치 위험)

**발생일**: 2026-07-03 (발견 계기: arXiv 2607.01224 "AutoMem" 논문을 Hermes 메모리 시스템과 비교 조사하던 중 부수적으로 발견 — 논문 자체와는 무관한 별개 버그)

**파일**: `modules/memory_refinement.py` — `auto_forget()`, `get_memory_health()`

**증상**: 잠재적 버그(아직 실제 불일치가 관측되진 않았으나 구조적으로 위험). `/memory forget`(삭제 대상 미리보기)와 `/memory health`(메모리 상태 리포트) 두 명령어가 "이 기억을 잊어야 하는가"를 각각 독립적으로 재구현한 별개의 코드로 계산하고 있었음.

**근본 원인**: `auto_forget()`과 `get_memory_health()` 둘 다 에빙하우스 망각곡선 공식(`stability = importance * 5.0`, `retention = exp(-days/stability)`)을 로컬에서 각자 복붙해 구현. 정작 이 공식의 정식 소스인 `modules/deriver_layer.py`의 `ForgettingCurve.retention()`(Lock Stack 파일)은 재사용하지 않음. 두 사본이 우연히 동일했지만, 한쪽만 수정되고 다른 쪽이 누락되면 `/memory health`가 "10개 삭제 가능"이라 보고하는데 `/memory forget`은 "삭제 대상 없음"이라 답하는 등 명령어 간 결과 불일치가 발생할 수 있는 구조였음.

**수정**:
```python
# 수정 전 (두 함수에 각각 중복)
stability = importance * 5.0
retention = round(math.exp(-days_elapsed / max(stability, 0.1)), 4)

# 수정 후 (단일 소스 재사용)
from modules.deriver_layer import ForgettingCurve
retention = ForgettingCurve.retention(importance, last_accessed)
```
로컬 `import math` 2곳도 더 이상 불필요해 제거. `deriver_layer.py`(Lock Stack) 자체는 수정하지 않음 — 기존 `ForgettingCurve`를 import해서 재사용만 함.

**검증**: `auto_forget(dry_run=True)`, `get_memory_health()` 둘 다 실제 `~/.hermes/memory/episodic_memory.json` 대상으로 재실행해 정상 동작 확인.

**재발방지**:
- 동일한 계산 공식이 여러 파일에 필요하면 반드시 단일 소스(가능하면 Lock Stack의 기존 클래스)를 import해서 재사용 — 로컬 재구현 금지
- Lock Stack 파일이라고 해서 "수정 못 하니 복붙하자"로 가면 안 됨 — **import해서 재사용하는 것은 Lock Stack 정책 위반이 아님**(파일 자체를 안 건드리므로), 이 경계를 명확히 구분할 것
- 코드 조사 중(다른 목적이더라도) 이런 중복 발견 시 논문/원래 작업과 무관해도 즉시 별도로 기록하고 수정
