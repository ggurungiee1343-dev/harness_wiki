# WebUI 멀티모델 통합이 왜 이렇게 오래 걸렸나?
### 2026-06-07 작업 사후 분석 (Post-mortem)

---

## TL;DR

> **단 하나의 기능**(Qwen-14B를 드롭다운에 표시하고 라우팅)을 추가하는 데 수 시간이 걸린 이유는,  
> **3~5겹의 독립적인 원인이 동일한 증상**("모델이 안 나타남 / 응답 없음")을 만들어냈기 때문이다.  
> 각 레이어를 하나씩 제거해야 다음 레이어가 보였다.

---

## 1. 작업 개요

**목표**: Hermes WebUI 드롭다운에 다음 4개 모델을 모두 표시하고 정상 응답 받기
- DeepSeek (기존, 정상)
- GPT OSS 120B (NVIDIA)
- Minimax M2.7 (NVIDIA)
- Qwen2.5-14B (로컬 llama-server)

**결과적으로 수정한 파일**: 5개  
**디버깅에 사용한 접근법**: 로그 추적, 코드 직접 탐색, 테스트 요청 반복

---

## 2. 왜 오래 걸렸나 — 레이어별 분석

### 🧅 레이어 1: "발견 가능한 첫 번째 원인"이 진짜가 아니었다

**처음 의심한 원인**: `config.yaml`에 `discover_models: false` 미설정  
→ Gateway가 llama-server에 `/v1/models` 요청 → `n_ctx=32768` 반환 → "컨텍스트 부족(32K < 64K)" 오류

**수정**: `discover_models: false` + `context_length: 65536` 추가  
**결과**: 오류 메시지는 사라졌지만 Qwen은 **여전히 드롭다운에 없음**

→ "분명히 고쳤는데 왜 안 바뀌지?" 상태로 진입. 이 구간에서 시간이 많이 소요됨.

---

### 🧅 레이어 2: 디스크 캐시가 변경을 묻었다

**두 번째 의심**: WebUI가 모델 목록을 디스크에 캐싱하고 있을 것  
→ `~/.hermes/webui/models_cache.json` 발견  
→ 내용을 보니 Qwen 등록 전의 구버전 데이터

**수정**: `rm ~/.hermes/webui/models_cache.json`  
**결과**: 이제 Qwen이 드롭다운에 보인다 (?)  
→ **아니, 여전히 없다**

→ 캐시를 지워도 변화 없음. "그럼 코드 자체가 문제"라는 결론으로 코드 분석 시작.

---

### 🧅 레이어 3: 하드코딩된 화이트리스트 (진짜 근본 원인)

**세 번째 분석**: `hermes-webui/api/config.py` 소스코드 직접 탐색  
→ 4813행에서 발견:
```python
_whitelist_keywords = ["gemma-4-26b", "deepseek-v4-flash", "gpt-oss-120b", "minimax-m2.7"]
```

**이것이 진짜 원인**. config.yaml이 아무리 올바르게 설정되어 있어도, 이 코드가 모델 목록을 필터링해서 일치하지 않는 모델은 UI에 표시조차 하지 않았다.

**왜 이게 있었나?**  
아마도 개발 과정에서 특정 모델만 노출하려는 임시 필터가 코드에 남아있었던 것으로 추정. 주석도 없고, 문서에도 언급 없음.

**수정**: `"qwen"` 추가  
**결과**: Qwen이 드롭다운에 표시됨 ✅

---

### 🧅 레이어 4: `@custom:` 접두사 — Gateway가 이해 못 하는 모델 ID 포맷

**새로운 문제**: Qwen을 선택했는데 응답이 없음. GPT OSS 120B는 `Unknown provider` 오류.  
→ Gateway 로그 분석:
```
Model ID received: @custom:qwen-14b:Qwen2.5-14B-Instruct-Q4_K_M.gguf
```

**원인**: WebUI는 모델을 `@custom:<slug>:<actual-model-name>` 형식으로 인코딩해서 Gateway에 전달. 하지만 Gateway(`api_server.py`)는 이 포맷을 모름. 그냥 통째로 모델명으로 처리 → config.yaml 매칭 실패 → 라우팅 불가.

**왜 DeepSeek는 됐나?**: DeepSeek는 custom_provider가 아니라 내장 provider를 사용하므로 이 인코딩 과정을 거치지 않음.

**수정**: `api_server.py`에 접두사 스트립 로직 3줄 추가  
**결과**: Qwen, GPT OSS 120B, Minimax 모두 라우팅 성공 ✅

---

### 🧅 레이어 5: `context_length` TypeError — 마지막 함정

**또 다른 오류**: `_resolve_custom_provider_by_model()`을 수정해서 `context_length`를 반환하도록 했더니, `AIAgent.__init__()`이 해당 파라미터를 몰라서 `TypeError` 발생.

**수정**: `runtime_kwargs.pop("context_length", None)` 한 줄 추가  
**결과**: 완전 해결 ✅

## 3. 시간을 잡아먹은 구조적 이유

### 이유 1: 증상이 모두 동일했다 ("모델이 없음 / 응답 없음")
각 레이어의 오류가 서로 다른 근본 원인임에도 동일한 증상을 만들어냄. "한 번 고쳤으니까 다음 문제로" 라는 것을 인식하기 어려웠다.

### 이유 2: 문서화되지 않은 동작이 많았다
- `_whitelist_keywords`: 소스코드 어디에도 문서화 없음
- `@custom:` 인코딩 포맷: Gateway 문서에 언급 없음
- 디스크 캐시 위치: 공식 문서 없음

### 이유 3: 수정 → 재시작 → 테스트 루프 비용
WebUI는 Node.js 프로세스라 매 수정마다 재시작 필요. 캐시까지 지워야 하는 경우도 있어서 검증 사이클이 길었다.

### 이유 4: 설치된 패키지 수정의 불편함
Gateway 코드가 venv 설치 패키지에 있어서:
- 소스 탐색이 까다로움 (경로 길고 숨어있음)
- IDE 지원 없이 수동 편집
- 패키지 업데이트 시 수정 사항 날아감

## 4. 앞으로 같은 문제 반복 방지

### 체크리스트: 새 custom_provider 추가 시

```
□ 1. ~/.hermes/config.yaml에 discover_models: false 추가
□ 2. hermes-webui/api/config.py의 _whitelist_keywords에 모델명 키워드 추가
□ 3. rm ~/.hermes/webui/models_cache.json (캐시 삭제)
□ 4. WebUI 재시작
□ 5. Gateway 재시작
□ 6. 드롭다운에서 모델 선택 후 "너 누구야?" 테스트
□ 7. Gateway 로그에서 @custom: 접두사 스트립 확인
```

### 모델 응답이 이상할 때 확인 순서

```
1. Gateway 로그 확인 (모델 ID가 어떻게 전달됐는지)
2. models_cache.json 삭제 (캐시 의심)
3. api/config.py whitelist 확인 (드롭다운 미표시 의심)
4. api_server.py @custom: 스트립 로직 확인 (Unknown provider 의심)
```

## 5. Hermes 시스템 프롬프트 10K 토큰 — 느린 것은 정상

Qwen-14B 응답이 약 2분 걸리는 것은 **버그가 아니라 설계된 동작**이다.

Hermes가 매 요청마다 보내는 시스템 프롬프트 구성:
- **Tool definitions**: 20개+ 도구 스키마 × 100~300토큰 = ~5,000토큰
- **Memory context**: 사용자 기억 + 프로젝트 상태 = ~2,000토큰
- **Soul/Persona**: Hermes 행동 지침 = ~1,000토큰
- **Skills**: 로드된 스킬 목록 = ~500토큰
- **합계**: ~8,000~12,000 토큰

Qwen2.5-14B @ llama-server: ~91 tokens/sec (Mac Studio 기준)  
10,000 토큰 ÷ 91 tokens/sec = **약 110초 (2분)**

KV 캐시가 워밍업된 이후에는 빠르지만, 첫 요청 또는 긴 공백 후 요청은 항상 느림.

**해결 방법이 있나?**  
- Hermes의 시스템 프롬프트 크기를 줄이려면 tool_use를 비활성화하거나 메모리를 끄면 됨
- 하지만 그러면 Hermes의 핵심 기능(도구 사용, 기억, 페르소나)이 비활성화됨
- **결론**: 로컬 14B 모델로 풀기능 Hermes를 운영하는 것은 속도 면에서 비효율적. 빠른 응답이 필요하면 DeepSeek(API) 또는 GPT OSS 120B(NVIDIA) 사용.
