## [2026-07-11] BUG-MJS-030: 미국/한국 장중 검색기 5종 "0건 지속" — 배선 누락(pochak) + 30분봉 페이지네이션 한계(samdoli) + RVOL 임계값 미스매치(samdoli/nongsa_danta)

**진단 방법**: BUG-MJS-028에서 쓴 진단 스크립트(`diagnose_zero_hit_screeners.py`, `diagnose_pochak_us_calibration.py`) 패턴을 재사용 — 새 진단 코드를 새로 짜지 않고, 기존 check_fn의 `details` dict(조건별 bool)를 실제 유니버스에 그대로 호출해 조건별 통과율(%)을 집계.

**원인 1 (배선 누락)**: `screener/run_scan.py`의 `US_SCREENERS["pochak"]` 딕셔너리에 `prepare_daily`/`prepare_5min`/`prepare_30min` 키가 아예 등록 안 돼 있었음(KR판(`KR_SCREENERS`)에는 등록돼 있었는데 US만 누락). raw OHLCV가 그대로 들어가 RVOL_20 등 파생 지표 컬럼 자체가 없어 daily_pass가 결정론적으로 항상 0%. `run_scan.py`에 신규 검색기 등록 시 US/KR 딕셔너리 양쪽 다 동일한 prepare_* 세트를 넣어야 하는데 US만 빠진 전형적 "형제 딕셔너리 불일치" 패턴.

**원인 2 (30분봉 페이지네이션 한계)**: `screener/data_loader.py`의 `KISClient.get_overseas_minute_ohlcv()`가 KIS API `NREC=120` 고정값에 페이지네이션이 없어, 30분봉이 최대 120개(실측 평균 105.6개)만 반환됨. samdoli의 일목균형표 156기간 조건(`cond_t`)과 pochak의 `d_ichimoku156` 조건이 rolling(156) 계산에 필요한 데이터 자체가 부족해 항상 NaN→False로 고정 — OR그룹으로 우회 불가능한 하드 AND 게이트라서 검색기 전체가 영구 0건이 됨.

**원인 3 (임계값 미스매치)**: samdoli(US/KR)·nongsa_danta(US/KR)의 RVOL 프록시 조건(X조건, "체결강도" 대체지표)이 임계값 1.5(g조건 3.0)로 설정돼 있었는데, 나스닥100 상위 100종목 실측 RVOL_20 분포는 median 0.57·90th %ile 0.88·99th %ile 1.08·최댓값 2.00 — 대형주 유니버스에서 1.5는 상위 1%만, 3.0은 0%만 통과하는 사실상 도달불가능한 임계값. BUG-MJS-028(2026-07-08, pochak RVOL 임계값 미스매치)과 정확히 같은 클래스.

**수정**:

- `screener/data_loader.py`: `KISClient.get_overseas_minute_ohlcv()`에 yfinance 우선 경로 신설(`_get_overseas_minute_yfinance` 메서드), 실패 시 기존 KIS API로 fallback.

- 배치 다운로드 fix: samdoli 500종목 스캔이 10분 36초로 완료(배치 다운로드 성공률 497/500=99.4%), 타임아웃 문제 해소.
- 최종 통합검증: `auto_scan_intraday.py --market us`/`--market kr` 전체 실행 — 한국 스캔 12/12 검색기 성공(shooting_kr 5개/2시그널, pochak_kr 13~17개 신호 — 이전 대부분 0), 미국 스캔도 shooting/chuddoli가 나스닥/러셀에서 1~3개 신호(이전 일주일 내내 거의 0).

**의도적으로 재보정하지 않은 것**: shooting/chuddoli의 ENV50(±3%)/BB50(2.2) 임계값 — 초기 44종목 스냅샷 진단에서 0~2.3%로 미스매치처럼 보였으나, 30분/5분봉 전체 바 기준 실측(ENV50 30분봉 21.2%, BB50 30분봉 8.1%, 5분봉 4~9%대)은 정상 범위였음. "0%"로 보였던 건 원인2(120봉 제한으로 인한 지표 불안정)와 소표본 스냅샷 변동성이 겹친 착시로 결론 — 실제 라이브 스캔에서 shooting/chuddoli가 1~3개씩 신호를 낸 것과 일치해 임계값은 그대로 둠.

**미해결로 남은 것**: samdoli의 "과잉 AND 체인" 구조(daily_base_pass∧fivemin_pass∧ema_pos_pass∧cond_t∧obv30_pass∧samdoli_type 6개 게이트 동시 통과 요구) — 수정 후에도 30종목 샘플 테스트에서는 여전히 0건. 단 breakout류 세부조건(BB78/ENV390/EMA30골든크로스)이 각각 3~23% 수준이라 500종목 전체 스케일에서는 가끔 뜰 것으로 예상, 며칠 관찰 필요. 버그가 아니라 confluence(다중조건 동시확인) 전략 설계 자체의 특성으로 판단 — MJ님과 재논의 필요.

**재발방지**:
1. 신규 검색기를 `run_scan.py`의 `US_SCREENERS`/`KR_SCREENERS`에 등록할 때 두 딕셔너리의 prepare_* 키 세트가 서로 일치하는지 diff 확인할 것(BUG-CORE-022·이번 사례처럼 "한쪽만 빠짐" 패턴이 반복됨).
2. 외부 API의 페이지네이션/봉개수 제한(`NREC` 등)이 있는 데이터소스는, 그 데이터를 쓰는 지표의 rolling window 길이(예: 156기간 일목균형표)가 실제로 채워지는지 최소 1종목 실측으로 확인한 뒤 검색기를 배포할 것 — 조건식이 맞아도 데이터 길이 부족으로 영구 NaN이 될 수 있음.
3. 0건 진단 시 임계값부터 의심하지 말고 진단 순서를 고정: ① prepare_* 배선 등록 여부 ② 지표 계산에 필요한 원천 데이터 길이/개수 확보 여부 ③ 그 다음에야 임계값 실측 대조. 이번 사례도 처음엔 임계값 문제로 보였으나 실제 최우선 원인은 배선 누락(원인1)·데이터 부족(원인2)이었음.
4. 신규 데이터소스(배치 다운로드 등)로 성능 fix를 적용했을 때는 실전 규모(500종목)로 반드시 재검증 — 소규모 검증만으로 "해결됐다"고 판단하면 안 됨(2026-07-09 LS API 사례와 동일 교훈, 05번 참조).

## [2026-07-08] BUG-MJS-029: 매수→매도 시그널 추적 시스템 전면 미작동 — batch_fill_returns.py fd 고갈 크래시(run_scan.py fix 미이식) + circle_date 소급 왜곡

**증상**: MJ님이 "매수→매도 완결 사이클로 로직/시그널 정합성을 확인해보자" 요청. Claude가 처음엔 "그런 사이클 추적 시스템이 없다"며 신규 백테스트 도구를 만들자고 제안했으나, MJ님이 "매수매도 프로세스 적어놓은 html파일 읽고 이야기해"라고 지적. `docs/quant_logic_analysis.html` 확인 결과 `screener/signal_tracker.py`→`tracker/signal_log.csv`가 이미 이벤트 기반 매수→매도 개별 추적(SELL_CONFIRMED/SELL_FALSE/TRAILING_GIVEBACK/TIMEOUT 4종 종료조건, 07-03 BUG-MJS-011/012 설계)을 하도록 만들어져 있었음. `tracker/signal_log.csv`(2,657행)를 실제로 열어보니 **전량 status=active**, `last_checked_date` 0건, `close_reason` 0건 — 설계는 있으나 단 한 번도 정상 작동한 적 없음.

**근본 원인**: 매일 갱신 담당 `screener/batch_fill_returns.py`(cron 평일 17:30)가 매번 **fd(파일 디스크립터) 고갈로 크래시**해 안의 `signal_tracker.update_positions()` 호출까지 도달 못 함. `results/fill_returns.log`에서 최소 2026-07-03/07-06/07-08 동일 `OSError: [Errno 24] Too many open files` 반복 확인. 이 fd 한도 상향 fix(`resource.setrlimit(RLIMIT_NOFILE, min(8192, hard))`)는 이미 `run_scan.py`에는 07-07 적용돼 있었음(quant.db 저장 3일 중단 사태, BUG-MJS-023/026 참조) — 그런데 완전히 별개 스크립트인 `batch_fill_returns.py`엔 이식되지 않아서 같은 근본 문제(fd 고갈)가 다른 파일에서 계속 반복되고 있었음. "한 곳에서 고친 인프라 버그가 같은 문제를 겪을 수 있는 다른 독립 스크립트엔 안 옮겨지는" 전형적 패턴.

**수정**: `screener/batch_fill_returns.py` 상단에 `run_scan.py`와 동일한 `resource.setrlimit` fix 추가(BUG-MJS-023/026 참조 주석 포함). 백업은 `screener/_backup_20260708/batch_fill_returns.py`.

**검증**: 실제 실행 — 크래시 없이 완주(ret_5d/10d/20d 총 3,071건 갱신), `update_positions()` US 1,485건·KR 571건 정상 갱신, `signal_log.csv`의 `last_checked_date`가 0건→2,056건(오늘 날짜)으로 실제 갱신 확인, 매도신호(`circle_date`) 49건 감지(전부 MACD_BB_SELL 타입).

**추가 발견 — circle_date 소급 정확도 왜곡 (MJ님이 직접 반박해서 찾아낸 부분)**: Claude가 처음엔 "SELL_CONFIRMED/TRAILING_GIVEBACK이 아직 하나도 안 걸린 건 데이터가 어려서(신호 발생 11일밖에 안 됨)"라고 **근거 없이 추정으로 답변**했으나, MJ님이 "그건 추정 아니냐, 매도신호가 과거에 떴었는데 내가 못 본 것 같다"고 반박. 실제 데이터를 재확인한 결과 49건에서 이미 매도신호가 잡혀 있었고, **전부 circle_date=2026-07-08(오늘)로 찍혀 있는 게 이상**했음. `signal_tracker.py:494-500` 코드 확인 결과, `update_positions()`는 **실행되는 순간의 최신 봉 데이터만 확인**해서 매도신호가 참이면 그 날짜를 circle_date로 기록 — **과거로 거슬러 올라가 "언제 처음 신호가 떴는지"는 확인하지 않는 구조적 한계**. 트래커가 6/29~7/7 사이 약 10일간 멈춰있었으니, 이 49건 중 상당수는 실제로는 그 기간 중 더 일찍 떴다가 트래커가 안 돌아서 놓쳤고, 오늘 처음 체크되면서 "오늘 발생"으로 실제보다 늦게 잘못 기록됐을 가능성이 높음.

**실질적 영향**: 정지 기간(6/29~7/7)에 걸친 코호트는 circle_date가 실제보다 늦게 찍혀 있어 "매도신호 후 3거래일 확인" 타이밍이 밀렸고, 같은 기간 MFE(max_favorable_pct, 최고수익률) 추적도 비어있었을 수 있어 실제 고점을 놓쳤을 가능성 있음. 이 왜곡은 정지 기간 코호트에만 해당되고, 크론이 정상화된 지금부터의 신호는 실시간으로 정확히 잡힘. **circle_date 소급 재계산(과거 봉 재스캔) 여부는 미착수 — MJ님 결정 대기.**

**재발방지**:
1. 인프라성 fix(fd 한도, 세션 재사용 등)를 한 스크립트에 적용했으면, **같은 인프라 자원을 쓰는 다른 독립 스크립트 목록을 grep으로 즉시 뽑아 동일 적용 여부를 그 자리에서 확인**할 것. `run_scan.py`와 `batch_fill_returns.py`는 완전히 별개 진입점이라 grep 없이는 서로의 존재를 인지하지 못함.
2. "0건/작동 안 함"을 관찰했을 때 "아직 조건이 안 됐다"는 식으로 **추정으로 답변 금지** — 반드시 로그(`results/*.log`)와 코드(`last_checked_date` 등 실제 컬럼값)로 원인을 확인한 뒤 답할 것.
3. 매수매도 프로세스처럼 이미 문서화됐을 법한 로직을 질문받으면, 새 도구 제안 전 `docs/` 폴더의 관련 html(`quant_logic_analysis.html` 등)에 이미 설계된 시스템이 있는지 먼저 확인할 것.

## [2026-07-03] BUG-010: 나스닥500 아침 스캔 "스캔 실패" — cron ulimit(FD 256개) 고갈

**증상**: `MJstock 미국(나스닥500) 아침 스캔` 텔레그램 메시지에서 우량주농사·세력주농사·초우량주 3개 검색식이 `❌ 스캔 실패`로 표시. 로그(`logs/scan_morning.log`)에는 서로 다른 무관한 티커마다 "possibly delisted", "unable to open database file" 에러가 여러 날에 걸쳐 반복 등장 — 얼핏 개별 티커 문제처럼 보이나 실제로는 아님.

**원인**: cron으로 실행되는 프로세스는 macOS 기본 `ulimit -n 256`(launchd 기본값)을 그대로 상속. `run_scan.py`가 나스닥100(top-n 500) 전체를 순회하며 yfinance 실패 시 KIS API로 폴백하는데, 이 과정에서 실패한 HTTP 커넥션이 파일 디스크립터를 계속 점유 → 스캔 후반부(400번째 티커 이후)에 256개 한도 초과 → `save_scan_result()`의 `matched.to_csv()` 호출 시점에 `OSError: [Errno 24] Too many open files`로 전체 프로세스 크래시(rc=1). `run_scan.py` 내부 per-ticker 예외처리(`try/except: continue`)는 정상 동작하지만, FD 고갈은 그 예외처리 범위 밖(pandas to_csv, sqlite 연결 등)에서 터지므로 못 잡힘. 로그에 남는 "delisted"/"unable to open database file" 메시지들은 `result.stderr[:400]` 잘림 때문에 보이는 지엽적 증상이고, 실제 크래시 원인(traceback)은 이 400자 제한에 잘려 로그에 안 남음.

**재현**: `ulimit -n 256; python run_scan.py --screen uryangju --universe nasdaq100 --top-n 500` → 동일 traceback 재현. 인터랙티브 셸(ulimit 기본 높음)에서는 동일 커맨드가 정상 완료됨 — 즉 코드 버그가 아니라 cron 환경 고유의 제약.

**수정 (2026-07-03)**: crontab의 아침/미국장중/한국장중 3개 스캔 라인에 `ulimit -n 4096;` 프리픽스 추가.
```
0 7 * * 1-5 ulimit -n 4096; cd /Users/bluesea/Applications/Mjstock && .venv/bin/python auto_scan_morning.py ...
```

**재발방지**:
- "스캔 실패" 발생 시 개별 티커 delisted 에러로 오진단하지 말 것 — 여러 날에 걸쳐 서로 다른 티커에서 반복되면 FD 고갈 의심
- `result.stderr[:400]` 잘림으로 인해 로그만으로는 진짜 원인 추적 불가 — 재현이 필요하면 반드시 `ulimit -n 256`으로 강제 재현할 것
- **Claude Code 셸(샌드박스)에서는 crontab 쓰기가 반영 안 됨**: `crontab -` 실행 시 root 소유 프로세스로 멈추고 exit 0을 반환하지만 `crontab -l` 재확인 시 변경 없음 (2026-06-30 최초 발견 당시엔 "타임아웃"으로 기록했으나, 실제로는 좀비 프로세스로 멈추고 거짓 성공을 리턴하는 패턴). crontab 수정은 항상 사용자가 Terminal.app에서 직접 실행해야 함 — Claude가 재시도해도 결과 동일.

### D. Llama-Server 멀티 슬롯 정합성 교정 (2026-06-05 추가 조치)

- **새로운 업데이트**: `~/.hermes/config.yaml`와 `~/Applications/venu/.hermes2/config.yaml`에 전체 toolsets를 포함하도록 2026-06-06에 적용되었습니다. 이제 두 Hermes 인스턴스 모두 모든 도구를 사용할 수 있습니다.
* **문제점**: 대화 세션이 다소 길어지면 에이전트가 본인이 방금 전까지 하던 작업 내역이나 생성한 파일들의 존재 자체를 잊어버려, "파일이 존재하지 않는다"며 추측성/환각 답변을 하는 기술적 한계 발생.
* **원인**: `com.bluesea.llama_server2.plist` 서비스가 `-np 2`로 구동되어 65,536 컨텍스트를 슬롯당 32,768토큰으로 쪼개고 있었음. Hermes 설정(`context_length: 65536`)에 맞춰 32k가 넘는 긴 메시지를 전송했을 때, Llama 서버단에서 대화 앞부분의 기억(파일 생성 내역 등)을 예고 없이 강제 Truncation(잘림) 처리하여 기억을 유실시킴. SWA 캐시 무효화로 인한 성능 저하도 동반됨.
* **조치**: Plist 파일 내 병렬 슬롯 수를 `-np 1`로 축소 조정하고 서비스를 재기동 완료. 슬롯당 65,536 컨텍스트를 온전히 확보하여 서버 수준에서의 강제 기억 상실 원인을 완벽히 예방 및 해결함.

### E. Bio-Memory Engine v9.3 — L2 메모리 블로트 리스크 대응 강제 증류 도입 (2026-06-05 추가 조치)

* **문제 인식**: L2 episodic_memory.json이 1.7MB / 83건으로 급증했으나, L3 패턴 학습이 Early Exit(rows=0)에 걸려 정체된 상태가 지속됨. 용량 기준 강제 증류가 없어 메모리 블로트 리스크 존재.
* **원인**: dreaming_v2.py의 L3 패턴 학습이 L2 증류 결과(rows)에만 의존했고, 용량 기준 체크가 없어 L2가 계속 팽창해도 강제 전이가 발생하지 않음.
* **조치 1 — bio_memory_engine.py**: `_get_l2_bytes()` 메서드 추가로 실시간 KB/MB 확인 가능. `get_memory_status()`에 바이트 정보 포함.
* **조치 2 — dreamer_layer.py**: `offline_consolidation_forced()` 추가 — 중요도 하위 50%를 조건 없이 강제 L3 전이. 용량 위기 시 자동 발동.
* **조치 3 — dreaming_v2.py**: `_run_offline_consolidation()`에 용량 위기(rows > 80 or bytes > 900KB) 탐지 로직 추가 → 강제 증류 호출. `_commit_to_l3_semantic()` atomic write 적용.
* **기대 효과**: L2가 1MB를 넘으면 중요도 무관 강제 증류로 L3 패턴 학습이 지속되며, write 중 crash에도 데이터 유실 없음.
