## [2026-06-24] BOT-001: Hermes1 봇 이중 재시작 충돌 (자주 뻑가는 고질병)

**배경**: Hermes1 텔레그램 봇이 재시작 후 자주 죽음. "PID 꼬임", "plist 문제"로 보였으나 실제 원인은 **재시작 메커니즘 이중화**.

**증상 패턴**:
- 재시작 시 `hermes.log`에 "⚠️ 다른 hermes_local 인스턴스가 이미 실행 중입니다. 종료합니다." 수십 줄 반복
- `hermes_error.log`에 텔레그램 `getUpdates` 200 OK 몇 번 후 갑자기 `Application is stopping` → `Application.stop() complete`
- `launchctl print`에서 `com.hermes.bot => disabled`

**원인** (botwatch.log의 `[botwatch] nohup 직접 실행 (PID xxxxx)` 줄이 결정적 증거):
1. `com.hermes.bot` launchd 서비스가 `disabled`로 드리프트 (재부팅/수동개입 등으로)
2. disabled → `launchctl kickstart` 조용히 실패 → `check_bot_alive.sh`의 폴백 `nohup` 직접 실행
3. nohup = launchd 미관리 **유령 프로세스** 생성
4. `com.hermes.bot`의 `KeepAlive=true`가 자기 관리 프로세스 부재 감지 → **별도 인스턴스 추가 기동**
5. 두 봇이 동일 토큰으로 텔레그램 `getUpdates` 동시 호출 → **Conflict** → 단일 인스턴스 보장 로직이 서로를 종료 → 무한 죽음/재시작 루프

**수정 (2026-06-24)**:
- `Scripts/check_bot_alive.sh` `_restart()`:
  - **nohup 폴백 완전 제거** (유령 프로세스 원천 차단 → launchd 단일 관리로 통일)
  - kickstart 전 `launchctl enable "gui/$(id -u)/com.hermes.bot"` 항상 선행 (disabled 드리프트 차단)
  - kickstart 실패 시 `launchctl bootstrap` 재시도로 미로드 케이스 커버

**검증**: 통제된 kickstart로 구 PID(36576)→신 PID(37180) 깨끗이 교체, `pgrep -f "Scripts/hermes_local.py" | wc -l` = **1** 확인, `Application started` 로그 + 하트비트 갱신 확인.

**재발방지**:
- `check_bot_alive.sh` 수정 시 **nohup 직접 실행 부활 금지** — 이중 인스턴스의 근원
- 봇 재시작은 **반드시 launchd 경로**(`launchctl enable` → `kickstart -k`)로만. 수동 `nohup python hermes_local.py` 금지
- `com.bluesea.hermes_local.plist.disabled`(구버전, `~/hermes/` 경로)는 **절대 enable하지 말 것** — 정식은 `com.hermes.bot`(`Scripts/` 경로)
- 진단 체크: `launchctl print gui/$(id -u)/com.hermes.bot | grep state` + `pgrep -f "Scripts/hermes_local.py" | wc -l`(=1)
- botwatch.log에 `nohup 직접 실행` 문구 보이면 = 이 수정이 되돌려진 것 → 즉시 점검

## [2026-06-24] ARCH-001: 논문 기반 검증층 붕괴 5경로 분석 및 방어책 적용

### 경로 1 — Governance Decay (arXiv 2606.22528)

**증상 패턴**: 히스토리 압축(compact_and_save) 후 LLM이 Lock Stack 규칙을 망각하고 수정 금지 파일 변경 시도 또는 경로 규칙 위반.

**원인**: 압축 시 초기 시스템 프롬프트가 사라지고 요약 텍스트만 남음 → 안전 제약 위반율 0%→59% (논문 실측).

**수정 (2026-06-24)**:
- `modules/history_manager.py` — `compact_and_save()` + `get_history_for_llm()` 양쪽에 `GOVERNANCE_ANCHOR` 메시지 삽입
- GOVERNANCE_ANCHOR 내용: Grounding 원칙 / Lock Stack 4개 파일명 / 경로 제한 (`~/Applications/` 외부 금지) / 지식 보존 / 증거 기반 보고

**재발방지**:
- 히스토리 압축 로직 변경 시 GOVERNANCE_ANCHOR 삽입 위치 보존 확인
- `get_history_for_llm()` 반환값 첫 메시지가 GOVERNANCE_ANCHOR인지 단위 테스트
- compact 전후 Lock Stack 위반 여부를 `/verify_harness`로 확인

### 경로 2 — Memory Contagion (arXiv 2606.23195)

**재발방지**:

## [2026-06-23] BUG-MJS-009: MJstock 장중 스캔 전체 crash — IndexError / KeyError / date 충돌 3종

**증상**: cron 22:30 자동 스캔 시 나스닥/러셀 5개 검색기 전부 returncode=1 실패. 텔레그램에 0종목 결과만 수신. 로그 STDERR에 `IndexError: single positional indexer is out-of-bounds` / `KeyError: 'close'` / `'date' is both an index level and a column label`.

**원인 3가지**:
1. **IndexError** — KIS API top-n 500 환경에서 일부 종목 빈 DataFrame(0행) 반환 → `check_fn` 내부 `df_daily.iloc[-1]` 실패. `prep_daily_fn` 이후에만 빈 가드가 있어, prep 전에 빈 df가 들어오면 보호 불가.

- US 스캔 `check_fn` 분기에 `samdoli` / `nongsa_danta` 케이스 누락 → `else: pass` 처리되어 빈 result 반환
- KR 스캔에 `prep_daily_fn` 호출 코드 자체가 누락 (미처 추가 안 됨)
- `auto_scan_intraday.py` 중복 실행 방지 장치 없어, 동시 실행 시 텔레그램 메시지 2배 발송

**수정 (2026-06-23)**:

## [2026-06-23] BUG-MJS-008: handlers/_base.py — executor 패키지 Python 3.14 SyntaxError (핸들러 전체 import 실패)

**증상**: 봇 기동 후 `/help`를 포함한 모든 명령어에 완전 무응답. 재시작해도 동일. 로그에 핸들러 관련 에러 없음.

**재발방지**:

## [2026-06-23] BUG-MJS-009: handlers/_system_ops.py — /restart_bot 레이스 컨디션으로 양쪽 인스턴스 동시 사망

**증상**: `/restart_bot` 실행 시 봇이 완전히 죽고 되살아나지 않음. botwatch가 "프로세스 없음" 루프 반복.

**원인**: 기존 순서 — NEW 프로세스 먼저 Popen → 2초 대기 → OLD SIGTERM. 2초간 두 인스턴스가 동시에 Telegram polling → Telegram이 409 Conflict 반환 → `hermes_local.py` Conflict 핸들러가 신규 프로세스에도 SIGTERM 발동 → OLD + NEW 양쪽 모두 사망 → "프로세스 없음" 상태 돌입.

**수정**: OLD를 즉시 먼저 SIGTERM → `shell=True` 옵션으로 `sleep 1 && python3 hermes_local.py` 실행하여 1초 후 NEW 기동. Telegram 단일 인스턴스 보장.

**수정 코드 핵심**:
```python
# OLD 먼저 종료
os.kill(old_pid, signal.SIGTERM)
# 1초 후 NEW 기동 (shell=True로 sleep 선행)
subprocess.Popen("sleep 1 && python3 hermes_local.py", shell=True, start_new_session=True)
```

**재발방지**:
- Telegram 봇 재시작 원칙: **OLD 먼저 종료 → NEW 기동** (역순 절대 금지)
- 두 인스턴스가 동시에 polling하면 Conflict 핸들러가 신규를 죽임 — 이 패턴 기억
- 재시작 구현 시 `shell=True + sleep` 선행 방식이 표준

* **문제점**: 대화 세션이 다소 길어지면 에이전트가 본인이 방금 전까지 하던 작업 내역이나 생성한 파일들의 존재 자체를 잊어버려, "파일이 존재하지 않는다"며 추측성/환각 답변을 하는 기술적 한계 발생.
* **원인**: `com.bluesea.llama_server2.plist` 서비스가 `-np 2`로 구동되어 65,536 컨텍스트를 슬롯당 32,768토큰으로 쪼개고 있었음. Hermes 설정(`context_length: 65536`)에 맞춰 32k가 넘는 긴 메시지를 전송했을 때, Llama 서버단에서 대화 앞부분의 기억(파일 생성 내역 등)을 예고 없이 강제 Truncation(잘림) 처리하여 기억을 유실시킴. SWA 캐시 무효화로 인한 성능 저하도 동반됨.
* **조치**: Plist 파일 내 병렬 슬롯 수를 `-np 1`로 축소 조정하고 서비스를 재기동 완료. 슬롯당 65,536 컨텍스트를 온전히 확보하여 서버 수준에서의 강제 기억 상실 원인을 완벽히 예방 및 해결함.

### E. Bio-Memory Engine v9.3 — L2 메모리 블로트 리스크 대응 강제 증류 도입 (2026-06-05 추가 조치)

* **문제 인식**: L2 episodic_memory.json이 1.7MB / 83건으로 급증했으나, L3 패턴 학습이 Early Exit(rows=0)에 걸려 정체된 상태가 지속됨. 용량 기준 강제 증류가 없어 메모리 블로트 리스크 존재.
* **원인**: dreaming_v2.py의 L3 패턴 학습이 L2 증류 결과(rows)에만 의존했고, 용량 기준 체크가 없어 L2가 계속 팽창해도 강제 전이가 발생하지 않음.
* **조치 1 — bio_memory_engine.py**: `_get_l2_bytes()` 메서드 추가로 실시간 KB/MB 확인 가능. `get_memory_status()`에 바이트 정보 포함.
* **조치 2 — dreamer_layer.py**: `offline_consolidation_forced()` 추가 — 중요도 하위 50%를 조건 없이 강제 L3 전이. 용량 위기 시 자동 발동.
* **조치 3 — dreaming_v2.py**: `_run_offline_consolidation()`에 용량 위기(rows > 80 or bytes > 900KB) 탐지 로직 추가 → 강제 증류 호출. `_commit_to_l3_semantic()` atomic write 적용.
* **기대 효과**: L2가 1MB를 넘으면 중요도 무관 강제 증류로 L3 패턴 학습이 지속되며, write 중 crash에도 데이터 유실 없음.

## 2026-06-12 버그 수정 및 재발방지

### BUG-001: episodic_memory.json 2.3MB 비대 (임베딩 인라인 저장)

**현상**: `episodic_memory.json`이 2.3MB+ 로 비대화. L2 로드/저장 속도 저하.  
**근본 원인**: `_promote_to_l2()`에서 384차원 float 배열(`embedding`)을 JSON 인라인으로 직렬화. 에피소드 200개 × ~3KB = 600KB+.  
**수정**: 인라인 `"embedding"` 필드 제거. turbovec `.npy` 외부 인덱스에만 저장. 기동 시 `_strip_inline_embeddings()`로 기존 파일 자동 마이그레이션.  
**재발방지**: `_promote_to_l2()`에 `# NO inline embedding — turbovec only` 주석 유지.

### BUG-002: L2 eviction `if` → `while` (1개만 제거하는 버그)

**현상**: L2가 용량 초과여도 재기동 후 1개만 evict되고 루프 종료.  
**근본 원인**: `if len(episodes) > L2_MAX_SIZE or ...` — `if`문으로 단 1회만 실행.  
**수정**: `while`로 변경 + `_get_l2_bytes()` 기반 실제 직렬화 크기 체크.  
**재발방지**: 용량 제한 로직은 반드시 `while` 사용.

### BUG-003: Model Collapse — LLM 응답 L2 자동 승격

**현상**: `assistant` 역할 발화가 MID 키워드를 포함하면 점수 3.0+으로 L2에 승격됨. LLM이 자기 응답을 다시 컨텍스트로 받아 다양성 붕괴.  
**근본 원인**: `ImportanceScorer.score()`에 role 기반 상한이 없었음.  
**수정**: `if role == "assistant": result = min(result, L1_TO_L2_THRESHOLD - 0.1)`  
**재발방지**: ImportanceScorer는 user 발화만 L2 후보로 삼아야 함. 논문: Model Collapse (2305.17493).

### BUG-MJS-007: /restart_bot → 봇 완전 사망 반복 (레이스 컨디션)

**발생일**: 2026-06-23
**파일**: `handlers/_system_ops.py` — `_restart_routine()`

**증상**: `/restart_bot` 실행 시 봇이 재시작되지 않고 완전히 죽어서 botwatch가 "프로세스 없음 — 자동 복구" 알림을 반복 발송

**근본 원인**: NEW 프로세스를 먼저 Popen으로 시작하고 2초 후 OLD를 SIGTERM으로 종료하는 순서였음.
- 두 인스턴스가 2초간 동시에 Telegram `getUpdates` 폴링
- Telegram이 신규 인스턴스에 409 Conflict 반환
- Conflict 핸들러(`os.kill(os.getpid(), SIGTERM)`)가 신규 인스턴스 자기 종료
- 이후 OLD 인스턴스도 자기 자신을 SIGTERM으로 종료
- 양쪽 모두 사망 → botwatch 반복 루프

**수정**:
OLD를 즉시 먼저 SIGTERM → `sleep 1 && python3 hermes_local.py` 로 1초 후 NEW 시작(shell로). 겹치는 구간 제로.

```python
# 수정 전 (문제)
sp.Popen([PYTHON, "-u", f"{SCRIPTS}/hermes_local.py"], ...)
await asyncio.sleep(2)
os.kill(os.getpid(), signal.SIGTERM)

# 수정 후 (정상)
old_pid = os.getpid()
sp.Popen(
    f"sleep 1 && {PYTHON} -u {SCRIPTS}/hermes_local.py >> ...",
    shell=True, start_new_session=True,
)
os.kill(old_pid, signal.SIGTERM)
```

**재발방지**:
- 봇 재시작 시 OLD 먼저 종료 → delay → NEW 시작 순서를 절대 원칙으로 유지
- NEW를 먼저 띄우는 방식은 Telegram 단일 인스턴스 제약상 항상 Conflict 위험
- `start_new_session=True` + `shell=True` 조합으로 NEW가 OLD의 SIGTERM 영향권 밖에서 시작되도록 보장
