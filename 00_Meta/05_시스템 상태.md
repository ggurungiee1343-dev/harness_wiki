**문제 1 — Zombie Poller (Hermes1 봇 7분 주기 좀비화)**:
- **증상**: 봇 프로세스는 살아있지만 (PID 존재, 메모리 점유) Telegram API 연결 0개, CPU 0%. 7분마다 launchd가 재시작해도 동일 패턴 반복. 3회 재현 확인 (PID 31208→32176→32956).

- **연관 파일**: `hermes_local.py` (run_polling 대체 + watchdog 60s + asyncio handler), `harness_agent.py` (auto_heal_loop bare except → 로깅), `com.hermes.bot.plist` (PYTHONUNBUFFERED + `-u` + ThrottleInterval=5)

**문제 2 — 에러 침묵 구조 (3중 차단)**:
- **증상**: 봇이 죽는데 로그가 전혀 없음. asyncio Task Exception, httpx 타임아웃, polling 실패 모두 silent.

- **수정**: asyncio 로거 ERROR 격상, bare except→로깅 교체, plist PYTHONUNBUFFERED=1 + `-u` 플래그, asyncio 예외 핸들러(traceback 포함) 등록.

- **수정**: 두 폴링 지점의 `time.sleep(1)` → `time.sleep(3)`으로 완화.
- **주의**: 최초 진단 시 "US/KR 검색기를 혼동한 사용자 실수"로 잘못 추정했었음 — 스크린샷으로 드롭다운≠본문 불일치가 명백히 확인되어 앱 버그로 정정. **사용자가 재현 가능한 구체적 증상(스크린샷 포함)을 제시하면 "혼동/실수"로 넘겨짚지 말고 코드부터 재확인할 것.**

**2. 웹 스캔 버튼이 scan_type="manual"로 안 찍히던 버그** (`app.py`, `screener/run_scan.py`)

- **문제**: `classify_tool()`이 도구명 기반 고정 2단계(INTERNAL/EXTERNAL) 분류만 — 런타임 이상 행동(반복 거부)에 따라 조정되는 메커니즘 없음

### 설계 변경 — 고정 기간 대기 → 이벤트 기반 즉시 종료 (MJ님과 합의)

기존 고정 10/20/30일 창 대신, 각 매수신호 건을 아래 3가지 이벤트 중 하나가 발생하는 즉시 종료·확정하는 방식으로 재설계:
- **SELL_CONFIRMED**: 매도신호(SHORT_PEAK/MACD_BB_SELL) 발생 후 3거래일 뒤 신호가 대비 -2% 이상 하락 확인
- **SELL_FALSE**: 매도신호 발생했으나 3거래일 뒤 반등해서 신호가 재돌파
- **TRAILING_GIVEBACK**: 매도신호 없이 최고수익률(MFE) 대비 -3%p 되돌림(단, 고점 2% 이상 났을 때만 적용)
- **TIMEOUT**: 위 셋 다 해당 없이 60거래일 경과
- **+5% 도달**(`reached_5pct_date`)은 종료 조건이 아니라 이정표로만 기록 — 매도 규칙(+5%)과 신호 검증 추적을 같은 기준으로 묶으면 신호의 진짜 잠재력(더 갈 수 있었는지)이 데이터에서 잘리기 때문

## 2026-07-03 — `modules/code_graph.py` 신규 (경량 코드베이스 지식그래프, 자체 구현)

**배경**: 외부 MCP 도구 `codebase-memory-mcp`(158개 언어 tree-sitter+LSP 지원, 25K 스타) 검토 — 유용해 보였으나 (1) 인덱스를 `~/.cache/`에 저장해 "`~/Applications/` 밖 파일 생성 금지" 규칙과 충돌, (2) Hermes는 거의 100% Python이라 158개 언어 지원이 과스펙. MJ님이 "MCP로 연결하지 말고 비슷하게 자체 구현 가능한지" 질문 → 가능 판단 후 자체 구현.

**신규 파일**: `modules/code_graph.py`
- 신규 의존성 0개 — Python 표준 라이브러리 `ast`(AST 파싱) + `sqlite3`만 사용
- MCP 서버 아님 — CLI 스크립트, Bash로 직접 호출해서 사용(프로토콜 레이어 없음, MJ님 요청대로)
- 인덱스 저장 위치: `Scripts/.hermes_code_graph.db` (본체 경로 안, `~/Applications/` 경계 준수)
- 핵심 기능 3개: `find_callers(함수명)`(누가 이 함수를 호출하나), `find_importers(모듈명)`(누가 이 모듈을 import하나), `get_file_summary(경로)`(파일 내 함수/클래스/import 목록)
- `_CodeVisitor(ast.NodeVisitor)`가 함수/클래스 스택을 추적하며 호출관계 추출 — 중첩 함수/메서드도 정확히 qualified name으로 기록

**검증**: `Scripts/` 전체(168개 파일, 실패 0) 0.25초에 인덱싱. 오늘 이전 세션에서 grep으로 수동 확인했던 `deriver_layer` importers 결과(`hermes_memory_patch.py`/`bio_memory_engine.py`/`memory_refinement.py`)와 **정확히 일치** 확인. `classify_tool`/`get_skill_lifecycle` 호출자 조회도 실제 코드와 일치.

**사용법**:
```bash
python3 modules/code_graph.py --rebuild                      # 재인덱싱 (코드 변경 후 필요)

python3 modules/code_graph.py --importers 모듈명               # import 관계 조회
python3 modules/code_graph.py --file modules/파일명.py         # 파일 요약
```
