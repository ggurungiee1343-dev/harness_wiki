# 🛡️ 하네스 컨트롤 (Harness Control) 분석 및 가이드

> [!NOTE]
> 이 문서는 텔레그램 메신저에서 작동하는 에이전트 제어 시스템인 **하네스 컨트롤**의 도입 배경, 핵심 작동 원리, 명령어 사용법, 그리고 기대 효용을 종합 분석한 개발 및 운영 가이드라인입니다.

---

## 1. 🔍 왜 하네스 컨트롤을 사용하는가? (이유)

대형 언어 모델(LLM) 기반의 코딩 에이전트는 뛰어난 생산성을 발휘하지만, 동시에 다음과 같은 치명적인 위험 요소를 안고 있습니다:
1. **오작동 및 시스템 파괴 (Hallucination):** 에이전트가 문법 오류가 있거나 필수 임포트(`Import`)를 누락한 불완전한 코드를 작성하고도 "수정을 완료했다"고 선언할 수 있습니다. 이로 인해 시스템 전체가 뻗는(Crash) 사고가 빈번하게 일어납니다.
2. **무단 파일 오염 및 유실:** 에이전트가 잘못된 판단으로 기존의 정상적인 작동 파일을 덮어쓰거나 훼손하여 시스템의 이전 상태를 유실할 수 있습니다.
3. **지식 부패 (Knowledge Staleness):** 시스템 가이드나 헌법 문서가 갱신되지 않고 방치되면, 에이전트가 최신 아키텍처 규칙을 인지하지 못한 채 구식 로직으로 작업을 진행하여 논리적 결함을 유발합니다.

하네스 컨트롤은 소프트웨어 공학의 신뢰성 검증 기법과 데이터베이스의 **ACID 트랜잭션** 개념을 개발 프로세스에 결합함으로써, **에이전트의 안전을 기계적으로 담보하고 시스템의 무결성을 100% 보증**하기 위해 도입되었습니다.

---

## 2. ⚙️ 하네스 컨트롤의 6-레이어 작동 원리 (원리)

하네스는 에이전트의 개발 라이프사이클 전체를 통제하는 **6단계 방어망 아키텍처(ACID v2.5)**를 기반으로 작동합니다.

| 단계 | 명칭 | 핵심 기능 | 비고 |
| :--- | :--- | :--- | :--- |
| **Layer 1** | **Single Source of Truth** | Git 형상 관리 하에서만 에이전트 작업을 개시하도록 보장. | 형상 일관성 |
| **Layer 2** | **Cold-Start Test** | `AGENTS.md`, `스크립트_정보.md`, `시스템 상태.md` 등 필수 가이드의 존재 유무 확인. | 지식 가시성 확보 |
| **Layer 3** | **Staleness Guard** | 필수 문서가 7일(임계값) 이상 수정되지 않고 방치될 경우 부패 경고 발생. | 지식 신선도 유지 |
| **Layer 4** | **DoD 기계 검증** | 에이전트 완료 선언 후 Python 문법 오류 및 임포트 정상 동작 여부 기계적 테스트. | 팩트 체크 |
| **Layer 5** | **ACID 격리 트랜잭션** | 별도 격리 브랜치(`agent/작업명-타임스탬프`)에서 작업을 수행하고, DoD 통과 시에만 `Atomic Commit` 수행. 실패 시 변경 전 상태로 **완전 롤백(Rollback)**. | 원자성, 격리성, 지속성 |
| **Layer 6** | **Diagnostic Loop** | 실패 원인을 5대 레이어로 정밀 분류하여 분석 보고서 축적 및 개선 가이드 제안. | 사후 피드백 |

## 3. 📱 명령어 사용 방법 (방법)

텔레그램 봇을 통해 언제 어디서나 하네스 시스템을 모니터링하고 제어할 수 있습니다.

### 1) `/harness [작업명세]` - 하네스 격리 파이프라인 개시
* **동작:** 
  1. Layer 1+2+3(Cold-Start 및 신선도) 검사를 실시합니다.
  2. 통과 시 격리된 Git 브랜치(`agent/job-timestamp`)를 자동으로 따서 에이전트에게 샌드박스 환경을 제공합니다.
  3. `PROGRESS.md`에 상태를 `IN_PROGRESS`로 영속화합니다.
  4. 에이전트가 작업을 수행하도록 대기시키고, 완료 시 검증할 수 있는 인라인 버튼을 화면에 띄웁니다.
* **사용 시점:** 에이전트에게 신규 기능 개발, 리팩토링, 버그 수정 등 시스템 구조가 바뀔 수 있는 작업을 지시할 때 반드시 첫 단계로 실행합니다.

### 2) `/hdod` - 즉시 DoD 기계 검증 실행
* **동작:** 정식 파이프라인 세션 외에, 현재 워킹 디렉토리 상태에서 필수 기계적 검증 명령어(문법 체크, 임포트 정상화 테스트 등)를 수동으로 강제 가동시킵니다.
* **사용 시점:** 에이전트가 작업 중일 때 또는 개발 과정에서 임시 검증이 필요할 때 단독으로 가동합니다.

### 3) `/hstatus` - 마지막 진단 리포트 조회
* **동작:** 가장 최근에 실패하여 롤백된 하네스 트랜잭션의 로그파일(`harness_diagnostic_log.json`)을 분석하여 에러 내역 및 5대 점검 리스트를 요약 보고합니다.
* **사용 시점:** 에이전트의 작업이 실패하여 하네스가 변경사항을 강제 롤백했을 때, 구체적으로 어떤 모듈이나 아키텍처 규칙이 깨졌는지 원인을 진단할 때 사용합니다.

### 4) `/hrollback` - 긴급 롤백
* **동작:** 커밋되지 않은 모든 파일 변경사항을 강제로 제거(`git reset --hard`)하고, 안전한 메인 브랜치로 긴급 복구(Rollback)합니다. (변경된 파일들은 `git stash`로 임시 대피되어 복구 가능합니다.)
* **사용 시점:** 에이전트가 루프에 빠져 잘못된 방향으로 폭주하거나, 수작업으로 시스템 상태를 긴급하게 이전 상태로 원복하고 싶을 때 실행합니다.

## 4. 📈 하네스 컨트롤의 효용성 (효용성)

1. **시스템 고장률 제로화:**
   에이전트가 작성한 코드에 치명적인 구문 에러가 있거나 라이브러리 참조 오류가 있을 경우, 메인 브랜치에 도달하지 못하고 격리 브랜치 단계에서 자동 강제 삭제(롤백)되므로 시스템 가동 시간(Uptime)이 완벽히 보장됩니다.
2. **에이전트 폭주 제어 및 격리:**
   샌드박스(Git Branch) 내에서만 파일 작업이 이뤄져, 에이전트가 무분별하게 원본 소스를 훼손하는 것을 시스템 레이어에서 구조적으로 차단합니다.
3. **기계적 신뢰 기반의 협업:**
   "다 고쳤습니다"라는 에이전트의 주관적인 응답 대신, 시스템 테스트 도구들이 실행한 팩트(DoD)에 근거하여 최종 커밋을 허용하므로 휴먼 에러 및 에이전트 에러를 완전히 배제할 수 있습니다.
4. **체계적인 트러블 슈팅:**
   작업이 무산되더라도 5대 오류 레이어 진단을 통해 지시의 모호성, 의존성 패키지 누락, 컨텍스트 단절 등의 원인을 명확히 짚어내어, 다음 번 작업 시 즉시 조치가 가능하도록 안내합니다.
