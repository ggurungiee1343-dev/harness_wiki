    13|## #001 — Gemma4 Connection Error → DeepSeek 자동 폴백
    14|
    15|- **발생 일시**: 2026-05-25 10:29
    16|- **영향 범위**: Hermes1 (WebUI + Gateway), 전체 세션 전환
    17|- **심각도**: 🟡 중간 (자동 폴백으로 서비스 연속성 유지)
    18|- **상태**: ✅ 해결 (자동 복구)
    19|- **지속 시간**: ~10초
    20|
    21|### 증상
    22|
    23|- Gemma4(llama.cpp, localhost:8080)로 진행 중이던 세션이 중단됨
    24|- WebUI/Telegram에 폴백 메시지 표시:
    25|  ```
    26|  ⚠️ 자동 폴백 발동 Gemma4 (로컬)이(가) 응답하지 않습니다.
    27|  → 폴백 체인을 통해 자동 전환합니다.
    28|  원인: Connection error.
    29|  ```
    30|- 이후 DeepSeek v4 Pro로 자동 전환되어 정상 응답
    31|
    32|### 원인 분석
    33|
    34|- **직접 원인**: llama-server에 대한 HTTP 연결 거부 (Connection error)
    35|- **간헐적 발생**: llama-server는 crash 없이 계속 실행 중 (PID 833)
    36|- **추정 원인**: 동시 요청 과부하, macOS 리소스 압박, 또는 모델 컨텍스트 초과 시 서버 일시적 무응답
    37|
    38|### 로그 증거
    39|
    40|```
    41|10:29:21 — Gemma4 API 콜 #4 성공 (4.0s, 캐시 100%)
    42|10:29:30 — stream_interrupt_abort (WebUI가 연결 중단)
    43|10:29:38 — 새 세션 DeepSeek v4 Flash로 전환
    44|```
    45|
    46|### 복구 방식
    47|
    48|- **자동 복구**: WebUI 폴백 체인이 DeepSeek으로 라우팅
    49|- **수동 조치 없음**: 사용자 개입 불필요
    50|- Hermes1 gateway config에는 `fallback_providers: []`로 설정되어 있으나, WebUI 자체 폴백 로직이 작동
    51|
    52|### 예방 조치
    53|
    54|- [ ] llama-server 재시작 스크립트/헬스체크 검토
    55|- [ ] Gemma4 Connection error 발생 빈도 모니터링

- **발생 일시**: 2026-06-07 15:41 ~ 15:57
- **영향 범위**: llama-server (8080 포트), Hermes1 텔레그램 봇
- **심각도**: 🟡 중간 (서비스 연속성 유지, 혼선 발생)
- **상태**: ✅ 해결 (2026-06-07 15:57)
- **지속 시간**: 약 16분

### 증상
1. Gemma4 → Qwen2.5-14B 전환 후 llama-server가 8080 포트에서 여전히 Gemma4로 응답
2. 두 번째 AI 에이전트가 Qwen2.5-14B를 `-c 65536`으로 올리자 OOM(메모리 부족) 발생, 서버 즉시 종료
3. 최종적으로 두 llama-server 프로세스가 동시에 떠있는 좀비 상태 발생:
   - PID 3488: Gemma4 26B (구 프로세스)
   - PID 3527: Qwen2.5-14B (새 프로세스, `-c 32768`)

### 원인

| # | 원인 | 상세 |
|---|------|------|
| ① | `launchctl kickstart`에 `-k` 옵션 누락 | 기존 Gemma4 프로세스가 kill 되지 않고 RAM에 계속 살아있음 (#022와 동일 패턴) |
| ② | 두 AI 에이전트 동시 작업 | 두 AI가 순차적이 아닌 동시에 llama-server 재시작을 시도하여 프로세스 혼재 |
| ③ | `-c 65536` 컨텍스트 OOM | Mac Studio 36GB 환경에서 Qwen2.5-14B(약 10GB) + 65536 컨텍스트(약 8GB+) = 메모리 초과 |

### 조치 완료 (2026-06-07 15:57)
- ✅ 좀비 Gemma4 프로세스(PID 3488) `kill -9`로 강제 종료
- ✅ Qwen2.5-14B 프로세스(PID 3527, `-c 32768`)는 정상 작동 확인 — 유지
- ✅ `com.bluesea.llama_server2.plist` context 수정: `65536` → `32768`
- ✅ Hermes1 봇 재시작 (`launchctl kickstart -k`)

### 교훈
- **컨텍스트 크기 가이드라인**: Qwen2.5-14B + Mac Studio 36GB에서 권장 context는 `-c 32768`. 65536은 OOM 유발.
- **좀비 프로세스 방지**: llama-server 재시작은 항상 `launchctl kickstart **-k**`를 사용. `-k` 없으면 기존 프로세스 유지.
- **다중 AI 작업 시**: 여러 AI가 동일 시스템에서 동시에 작업할 경우, llama-server 재시작처럼 시스템 전역에 영향을 주는 작업은 한 번만 수행해야 함. 완료 후 `ps aux | grep llama-server`로 중복 프로세스 점검 필수.

### 관련 파일
- `/Users/bluesea/Library/LaunchAgents/com.bluesea.llama_server2.plist` — context 32768로 수정

## #024 — WebUI 멀티모델 통합 장애 (Qwen/GPT-OSS/Minimax 드롭다운 미표시 및 라우팅 실패)

- **발생 일시**: 2026-06-07 (세션 전체)
- **영향 범위**: Hermes WebUI (8787), Hermes Gateway (8642)
- **심각도**: 🔴 높음 (Qwen, GPT OSS 120B, Minimax M2.7 세 모델 모두 사용 불가)
- **상태**: ✅ 완전 해결 (2026-06-07)
- **지속 시간**: 수 시간 (원인이 3겹으로 중첩되어 디버깅 장기화)

### 증상

1. Hermes WebUI 모델 드롭다운에 Qwen-14B가 표시되지 않음 (DeepSeek만 표시)
2. GPT OSS 120B 선택 시 → 응답 없음 (`Unknown provider 'custom:gpt-oss-120b-nvidia'` 오류)
3. Minimax M2.7 선택 시 → 응답은 오지만 "나는 무료 Minimax를 쓰는 건가요?" 라는 엉뚱한 답변
4. DeepSeek만 정상 동작

### 원인 분석 — 3겹 중첩 장애

#### Layer 1: config.yaml `discover_models` 문제 (부분 원인)
- `custom_providers`에 `discover_models: false` 설정 누락 시, Gateway가 `GET /v1/models`로 로컬 llama-server를 프로브
- GGUF `n_ctx` 메타데이터가 `32768`을 리포트 → Hermes 최소 요구치 64K 미달 → 모델 등록 실패
- **수정**: `discover_models: false` + `context_length: 65536` 명시 추가

#### Layer 2: WebUI 하드코딩 화이트리스트 (진짜 근본 원인)
- `hermes-webui/api/config.py` 4813행에 드롭다운 필터 존재:
  ```python
  _whitelist_keywords = ["gemma-4-26b", "deepseek-v4-flash", "gpt-oss-120b", "minimax-m2.7"]
  ```
- `"qwen"`이 목록에 없어 Qwen은 아무리 config.yaml을 수정해도 드롭다운에 표시되지 않았음
- **수정**: `"qwen"` 추가

#### Layer 3: 디스크 캐시 (차단 원인)
- `~/.hermes/webui/models_cache.json`에 구버전 모델 목록이 캐시됨
- 코드를 수정해도 캐시가 살아있어 UI는 계속 구버전 모델 목록 표시
- **수정**: `rm ~/.hermes/webui/models_cache.json` 후 재기동

#### Layer 4: `@custom:<slug>:model` 접두사 미스트립 (라우팅 실패 원인)
- WebUI는 모델을 `@custom:qwen-14b:Qwen2.5-14B-Instruct-Q4_K_M.gguf` 형식으로 Gateway에 전달
- Gateway(`api_server.py`)는 이 접두사를 이해하지 못해:
  - Qwen: 컨텍스트 창 32768 오류 (config 매칭 실패 → llama-server n_ctx 직접 조회)
  - GPT OSS 120B: `Unknown provider 'custom:gpt-oss-120b-nvidia'` 오류
  - Minimax: 내장 `minimax` provider(무료 플랜)로 잘못 라우팅
- **수정**: `api_server.py`에 접두사 스트립 로직 추가:
  ```python
  if _raw_model.startswith("@") and ":" in _raw_model:
      _parts = _raw_model.split(":", 2)
      if len(_parts) == 3:
          _raw_model = _parts[2]   # "@custom:slug:actual-model" → "actual-model"
          model_name = _raw_model
  ```

#### Layer 5: `context_length` TypeError (부가 버그)
- `_resolve_custom_provider_by_model()`이 `context_length` 키를 포함한 dict를 반환
- 이를 `**runtime_kwargs`로 `AIAgent.__init__()`에 전달 시 TypeError 발생
- **수정**: `runtime_kwargs.pop("context_length", None)` 추가

### 수정된 파일

| 파일 | 위치 | 수정 내용 |
|---|---|---|
| `config.yaml` | `~/.hermes/config.yaml` | Qwen-14B에 `discover_models: false`, `context_length: 65536` 추가 |
| `api/config.py` | `hermes-webui/api/config.py` | `_whitelist_keywords`에 `"qwen"` 추가 |
| `api_server.py` | `venu/venv/.../gateway/platforms/api_server.py` | `@custom:` 접두사 스트립 로직 추가 |
| `run.py` | `venu/venv/.../gateway/run.py` | `_resolve_custom_provider_by_model()` context_length 반환 추가 |
| `models_cache.json` | `~/.hermes/webui/models_cache.json` | 캐시 파일 삭제 |

### 결과

| 모델 | 수정 전 | 수정 후 |
|---|---|---|

| GPT OSS 120B (NVIDIA) | ❌ Unknown provider | ✅ 정상 응답 |

### 교훈

1. **WebUI 화이트리스트 존재**: 새 custom_provider 추가 시 `hermes-webui/api/config.py`의 `_whitelist_keywords`도 반드시 확인
2. **디스크 캐시 먼저 삭제**: config 수정 후 변화가 없으면 `rm ~/.hermes/webui/models_cache.json`
3. **venv 패키지 수정 주의**: `pip upgrade`시 `api_server.py`, `run.py` 수정 사항이 덮어써짐. 업그레이드 전 패치 내용 백업 필요
4. **로컬 모델 느린 응답은 정상**: Hermes 시스템 프롬프트가 ~10K 토큰이므로 14B 로컬 모델에서 첫 응답이 2분 걸리는 것은 버그가 아님
5. **원인 중첩**: 단일 증상(Qwen 드롭다운 미표시)의 원인이 config → 캐시 → 화이트리스트로 3겹으로 존재. 표면적 수정만으로는 해결 안 됨
