## 🛠 Part 1: 시스템 개선 제안

> 질문: "니가 지금 나랑 일하면서 파일 만들고 시스템 구축하는데 니생각에 내가 너 도워줄건 없어? 도는 니가 이렇게 구축했으면 좋겠다라고 생각한건 없니?"

### 1A. Agent가 MJ님에게 필요한 것

#### ① 변경 전 Diff 미리보기 권한
- 현재: 파일을 바로 patch/write
- 제안: `git diff`를 보여주고 **승인받은 후에만 적용**하는 워크플로우
- 효과: #017 같은 실수나 예상치 못한 부작용 사전 차단

#### ② "이건 내 의도대로 한 거다" 플래그
- Agent가 "이게 맞나?" 망설이는 상황에서 MJ님이 **✅ / 🚫** 단축 이모지로 의도 명시
- 효과: Agent 추측 빈도 감소

#### ③ 시스템 로그 접근 단축 경로
- launchd 로그, bot.log, gateway.log를 하나의 명령어로 덤프하는 스크립트
- 효과: 진단 속도 2~3배 향상

### 1B. 시스템에 추가할 개선사항

#### ① 단위 테스트 인프라 (가장 시급)

| 증상 | 원인 | 테스트로 차단 가능? |
|:---|:---|:---:|
| #013 Dreaming import 누락 | MemoryEngine import 없음 | ✅ `import modules.memory_engine` 호출 테스트 |
| #014 Ingest 인자 중복 | event_loop=... 중복 전달 | ✅ `IngestEngine()` 생성 테스트 |
| #015 Recent 인자 불일치 | get_recent_context(n_results=5) 시그니처 불일치 | ✅ 함수 호출 시그니처 검증 테스트 |
| #016 DummyRouter 전파 | `from X import Y` 값 복사 문제 | ✅ router 인스턴스 타입 검증 테스트 |

- Python 타입 힌트 + `pytest` 기반
- 각 모듈 `__init__` 호출 테스트 → 인자 불일치 즉시 발견
- router import 테스트 → DummyRouter 전파 즉시 발견
- Telegram 핸들러 mock 테스트 → callback NoneType 방어 즉시 발견
- **ROI**: #013~#016 합계 **~48시간 생산성 손실** vs 테스트 구축 **1일 투자**

#### ② Git Workflow 정착
```
main (안정)
  └─ feature/xxx 브랜치 생성 → 수정 → MJ님 확인 → main merge
```
- #017 같은 오류를 merge 전에 걸러냄
- git_manager.py는 이미 존재 (HERMES.md 규칙 6)

#### ③ 모듈 헬스체크 + 알림
- #013~#016: 24시간 동안 조용히 죽어있었음
- 각 모듈에 `/health` 엔드포인트 또는 시작 시 self-diagnostic 로그
- system_monitor.py(HERMES.md 등록)와 연동 가능
- 효과: "조용한 실패"를 즉시 알림으로 전환

#### ④ ADR (Architecture Decision Record)
- MJ님 머릿속에만 있는 아키텍처 결정을 문서화
- 예: "왜 Bot→llama-server 직결 vs Gateway 경유?"
- 효과: Agent가 같은 결정을 재추론할 필요 없음, MJ님 재설명 불필요

## 🔬 Part 2: 하네스 기여도 분석

> 질문: "지금의 답변이 딥씨크 니가 좋은 ai라서 나오는 답변이니? 아니면 내가 구축한 하네스의 도움으로 나온 답변이니?"

### 2A. 답변의 3개 Layer 분해

| Layer | 설명 | 기여도 |
|:---|:---|:---:|
| **Layer 1: 순수 모델 지식** | pytest, ADR, Git 전략, health check — 모든 LLM이 아는 일반론 | ~15% |
| **Layer 2: 하네스 문서 + 메모리** | 장애 기록 구체적 사례, HERMES.md 모듈 목록, 시스템 인벤토리 — **MJ님의 인프라** | **~70%** |
| **Layer 3: 크로스 합성 추론** | 문서 간 연결 + ROI 계산 + 우선순위 판단 — 모델+하네스 협력 | ~15% |

### 2B. 구체적 데이터 출처 추적

| Agent 답변 내용 | 출처 (하네스 요소) |
|:---|:---|
| "#013~#016 24시간 지속 버그" | 장애 기록.md |
| "48시간 생산성 손실 (24h×2회)" | 장애 기록.md → Agent 계산 |
| "import 누락/인자 불일치" | 장애 기록.md 원인 분석 표 |
| "17개 모듈, handlers/ 패키지" | HERMES.md + 시스템 인벤토리.md |
| "system_monitor.py 존재" | HERMES.md 모듈 목록 23행 |
| "git_manager.py 있음" | HERMES.md 규칙 6 |
| "Launchd 로그 경로" | 메모리 (Hermes2 plist 경로) |
| "Telegram 버튼 콜백 가능" | 장애 기록 #004 (mode_callback) |
| "변경 전 Diff 미리보기 필요" | #017 사건 (직접 경험) |

### 2C. 크로스-도큐먼트 합성 예시

```
[장애 기록.md]      #013~#016 24시간 지속
      ↓ (모델이 연결)
[HERMES.md]         system_monitor.py 존재
      ↓ (모델이 추론)
→ "system_monitor가 module health는 안 본다"는 결론
→ "health check 추가" 제안 구체화
```

## 🎯 Part 3: Gemma4 최적화 전략

> 결론: "가장 약한 모델 기준으로 최적화하면 모든 모델이受益"

### 3A. 세 가지 최적화 방향

#### ① 문서 축소 + 핵심 선배치
- 현황: 장애 기록.md 593줄 → Gemma4 32K context에서 긴 문서 핵심 놓침
- 해결: 상단에 **1~2줄 요약 + 핵심 테이블** 먼저 배치, 상세 로그는 뒤로
- 효과: Gemma4 정확도 ↑, DeepSeek도 더 빠름

#### ② 포인터 패턴 → 복사 패턴
- 현황: constitution.local.md "§2 참조" 방식 → Gemma4가 다른 문서 추가 로드 필요
- 문제점: Gemma4는 문서 간 추론(크로스-레퍼런스)이 약함
- 해결: 핵심 규칙은 각 문서에 직접 중복 기재 (DeepSeek은 중복에 무해) ✅구현됨 (constitution.local.md v1.2, 2026-05-26)
- 효과: Gemma4가 단일 문서만 읽어도 모든 규칙 파악 가능 ✅구현됨 (constitution.local.md v1.2, 2026-05-26)

#### ③ 결정 근거를 문서 앞쪽에
- 현황: ADR 부재 → Agent가 "왜 이렇게 했는지" 추론해야 함
- 해결: 결정 기록 1줄 메모 (예: "Bot→llama-server 직결: Gateway 충돌 #008 때문")
- 효과: 모든 모델이 재추론에 토큰 낭비하지 않음

### 3B. 모델별 특성 차이

| 특성 | DeepSeek v4 Flash | Gemma4 27B |
|:---|:---|:---|
| Context 길이 | 128K | 32K |
| 문서 간 추론 | 강함 (크로스 합성 가능) | 약함 (단일 문서 선호) |
| 긴 문서 이해 | 우수 | 중간 (중요 정보 누락 가능) |
| ROI 계산 능력 | 자연스러움 | 가능하나 부자연스러움 |

## 💡 Part 4: 핵심 인사이트 요약

1. **하네스 기여도 70%**: Agent의 구체적인 제안은 모델 성능보다 MJ님의 문서 인프라(장애 이력, HERMES.md, 메모리)에서 나옴
2. **가장 약한 모델 기준 최적화**: Gemma4에 맞게 문서를 다이어트하면 DeepSeek도 더 잘 이해함 (Weakest Link Principle)
3. **테스트 인프라가 최우선**: #013~#016 48시간 손실을 보면 단위 테스트 구축 ROI가 가장 높음
4. **ADR 필요**: 결정 근거를 문서화하면 모델 추론 비용 절감 + 결정 일관성 향상
5. **문서 구조 전환**: 포인터(참조) 패턴 → 복사(중복) 패턴으로 전환 시 Gemma4 성능 향상
