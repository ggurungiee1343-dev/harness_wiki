## 🔴 결함 #1: Zombie Poller (PTB run_polling 블로킹)

### 1.1 시스템 컨텍스트

```
Hermes1 봇 (hermes_local.py)
  └── python-telegram-bot v22.5
      └── Application.run_polling()
          └── asyncio event loop
              └── loop.run_forever() ← 절대 리턴하지 않음
```

python-telegram-bot(PTB)은 Telegram 봇 프레임워크의 표준 라이브러리다. `Application.run_polling()`은 모든 예제 코드에서 사용하는 **공식 권장 패턴**이다.

### 1.2 증상 상세

1. **프로세스 상태**: `ps aux | grep hermes_local` → PID 존재, 메모리 점유, CPU 0%
2. **네트워크 상태**: `lsof -i @149.154.166.110` → Hermes1 연결 0개 (Hermes2는 2개 ESTABLISHED)
3. **로그 상태**: stderr 로그 마지막 타임스탬프가 변경되지 않음 (8KB block-buffer가 차기 전까지 silent)
4. **스레드 상태**: `ps -M PID` → 모든 스레드 'S'(Sleeping)
5. **스택 트레이스**: `sample PID 2` → 모든 샘플이 `select_kqueue_control_impl(kevent_id)` — 즉, 커널 이벤트 대기. Python 프레임 전혀 없음.
6. **launchd 인식**: exit code가 발생하지 않으므로 KeepAlive가 트리거되지 않음. 사람이 SIGKILL로 죽여야 재시작됨.

### 1.3 재현 패턴

```
time 0:00  Application started (PID 31208)
time 0:05  User sends /help → bot responds OK
time 0:10  Test script calls getUpdates → 409 Conflict 발생
time 0:11  PTB updater stops → polling coroutine 종료
           하지만 event loop는 계속 실행됨 (auto_heal_loop, MemoryConsolidator 등)
time 7:00  사용자: "봇이 안 움직여요"
           조사 결과: PID는 살아있고, CPU 0%, Telegram 연결 0개
time 7:01  SIGKILL → launchd 재시작 (PID 32176)
time 7:10  동일 패턴 반복
```

### 1.4 근본 원인

```python
# PTB v22.5 Application.run_polling() 내부 구조 (요약)
def run_polling(self, ...):
    loop = asyncio.new_event_loop()
    try:
        loop.run_until_complete(self.initialize())
        loop.run_until_complete(self.start())
        loop.run_until_complete(self.updater.start_polling(...))
        loop.run_forever()  # ← 이 줄이 절대 리턴하지 않음
    finally:
        loop.close()
```

`loop.run_forever()`는 이벤트 루프가 명시적으로 중지(`loop.stop()`)되지 않는 한 영원히 실행된다. PTB의 Updater가 409 Conflict(중복 폴링 감지)로 중단되어도, `loop.run_forever()`는 다른 태스크(`auto_heal_loop`, `MemoryConsolidator`)가 계속 실행 중이므로 리턴하지 않는다.

**Conflict 발생 시 PTB 내부 동작:**
1. `Updater.start_polling()` 내부에서 `getUpdates` long-poll 실행 중
2. 다른 프로세스가 같은 토큰으로 `getUpdates` 호출 → Telegram이 409 Conflict 응답
3. PTB의 httpx transport가 ConflictError 발생
4. `global_error_handler`가 WARNING 로그 출력
5. Updater가 `running = False`로 설정하고 polling 중단
6. **그러나 이 시점에서 `run_polling()`의 `loop.run_forever()`는 계속 실행 중**
7. 프로세스는 좀비로 생존

### 1.5 수정 내용

**Before:**
```python
# 절대 리턴하지 않음
app.run_polling()
```

**After:**
```python
async def _run_polling_managed():
    async with app:
        await app.start()
        await app.updater.start_polling(drop_pending_updates=True)
        logger.info('📡 Polling started — monitoring health every 15s')
        while app.updater.running:
            await asyncio.sleep(15)
        logger.warning('[polling] Updater stopped — exiting for restart')

try:
    asyncio.run(_run_polling_managed())
except Exception as poll_err:
    logger.error(f'❌ Polling failed: {poll_err}', exc_info=True)
finally:
    sys.exit(0)  # launchd KeepAlive가 재시작
```

**핵심 차이:** `updater.running`을 직접 모니터링하여 polling 중단 시 15초 내 감지하고 `sys.exit(0)`으로 깔끔하게 종료. launchd의 `KeepAlive=true`가 5초 후 새 인스턴스 시작.

### 1.6 보조 안전장치

- **asyncio 예외 핸들러**: 모든 unhandled task exception을 traceback 포함 로깅 (line 501-527)
- **60초 watchdog**: `bot.get_me()` 주기적 호출로 연결 상태 확인
- **asyncio 로거**: `ERROR` 레벨로 격상 (WARNING 시 Task Exception 로그 차단)
- **launchd ThrottleInterval=5**: 재시작 간격 제어 (무한 재시작 루프 방지)

## 🟡 결함 #2: 에러 침묵 구조 (Triple Silent Failure)

### 2.1 시스템 컨텍스트

```
봇 프로세스에서 예외 발생 시:
  
  Layer 1: asyncio logger
    logging.getLogger("asyncio").setLevel(logging.WARNING)
    → "Task exception was never retrieved" 로그 차단 (WARNING 수준)
  
  Layer 2: Bare except blocks
    except Exception:
        pass
    → 2개 위치에서 모든 예외 침묵
  
  Layer 3: stderr buffering
    plist: PYTHONUNBUFFERED 없음
    → launchd redirection으로 stderr가 block-buffered (8KB)
    → crash 로그가 파일에 안 써짐
```

### 2.2 발견된 침묵 지점

**위치 1 — `hermes_local.py` auto_heal_loop (line 501-509):**
```python
async def _auto_heal_loop():
    while True:
        try:
            _ha_mod.sys_mon.auto_heal(...)
        except Exception:
            pass  # ← 5분마다 실행되는데 모든 오류 침묵
        await _asyncio.sleep(300)
```

**위치 2 — `harness_agent.py` auto_heal_loop (line 779-780):**
```python
async def auto_heal_loop():
    while True:
        try: sys_mon.auto_heal(...)
        except: pass  # ← 독립 실행 시 사용, 동일 패턴
        await asyncio.sleep(60)
```

### 2.3 근본 원인 분석

이 3중 차단 구조는 "의도적으로 로그 노이즈를 줄이자"는 개별 결정들이 **누적된 결과**였다:

1. **asyncio WARNING 설정**: httpx의 `getUpdates` 200 OK 로그가 너무 많아서 WARNING 이상만 남기기로 결정. 이때 asyncio 로거도 같이 WARNING으로 설정하면서 **"Task exception was never retrieved"** 같은 fatal 로그도 함께 차단됨. 이 로그는 polling coroutine이 침묵히 crash했을 때 유일한 단서다.

2. **Bare except pass**: `auto_heal_loop`에서 `sys_mon.auto_heal()`이 실패해도 정상 동작에 영향이 없을 거라고 판단. 하지만 이 determined silence로 인해 `auto_heal` 함수 내부의 모든 버그가 완전히 가려짐.

3. **PYTHONUNBUFFERED 누락**: launchd의 StandardErrorPath로 stderr를 리다이렉트할 때 Python의 기본 buffering 모드는 **block-buffered**(보통 8KB). stderr 출력이 8KB 미만이면 프로세스가 종료될 때까지 파일에 기록되지 않음. 따라서 봇이 좀비로 살아있는 동안 발생한 모든 stderr 출력은 메모리 버퍼에 갇힘.

### 2.4 수정 내용

```python
# Layer 1 fix: asyncio logger를 ERROR로 격상
logging.getLogger("asyncio").setLevel(logging.ERROR)

# Layer 1 보강: asyncio exception handler 등록 (traceback 포함)
_loop.set_exception_handler(_task_exception_handler)

# Layer 2 fix: bare except → 로깅
except Exception as heal_err:
    logger.warning(f'[auto_heal] 실행 실패: {heal_err}')

# Layer 3 fix: plist PYTHONUNBUFFERED
# com.hermes.bot.plist:
#   <key>EnvironmentVariables</key>
#   <dict><key>PYTHONUNBUFFERED</key><string>1</string></dict>
#   ProgramArguments에 -u 플래그 추가
```

### 2.5 탐지 방법 (다른 AI용)

이 패턴을 탐지하려면:

## 🟠 결함 #3: Gemma4 GGUF Chat Template 버그

### 3.1 시스템 컨텍스트

```
사용자 → /ask 또는 /ingest 명령어
  → _call_primary_with_fallback(messages, primary_mode="Gemma4")
    → _call_local(messages)
      → local_client.chat.completions.create(model="local-model", messages=...)
        → llama-server (port 8080)
          → GGUF 내장 Jinja template → 메시지 포맷
          → Gemma4 26B 추론
          → 응답: 빈 문자열 ("")
```

### 3.2 재현

```python
# ❌ 항상 빈 문자열 반환
client.chat.completions.create(
    model="local-model",
    messages=[{"role": "user", "content": "Hi"}]
)
# → response.choices[0].message.content = ""

# ✅ 정상 동작
client.completions.create(
    model="local-model",
    prompt="<start_of_turn>user\nHi<end_of_turn>\n<start_of_turn>model\n"
)
# → response.choices[0].text = "Hello! How can I help you?"
```

### 3.3 근본 원인

이 특정 GGUF 파일(`gemma-4-26B-A4B-it-UD-Q4_K_S.gguf`)의 메타데이터에 포함된 `tokenizer.chat_template` (Jinja2 템플릿)이 손상되었거나 llama.cpp의 Jinja 엔진과 호환되지 않는다.

**증거:**
1. `chat.completions` → 항상 빈 문자열 (HTTP 200 성공, content만 없음)
2. `completions` (raw prompt) → 정상 응답
3. 수동 Gemma4 포맷(`<start_of_turn>user...<end_of_turn>`) → 정상 응답
4. system 메시지 포함 시에도 빈 문자열 (Jinja template 변환 실패 추정)
5. prompt_tokens는 정상 카운트 (17 tokens, 51 tokens 등) → 모델이 입력은 받지만 출력을 생성 못 함
6. completion_tokens도 정상 카운트 (10, 50, 100 tokens) → 모델이 "빈 문자열을 50번 생성"하고 있음

### 3.4 영향 범위

- **전면적**: 모든 instruction-following 작업이 Gemma4 모드에서 실패
- **은밀함**: 예외 발생이 아니라 정상 응답(빈 문자열)을 반환하므로 fallback 체인이 트리거되지 않음. `_call_primary_with_fallback`의 1차 시도가 예외 없이 성공(빈 문자열 반환)하므로 2차/3차 fallback으로 진행되지 않음
- **사용자 인지 불가**: 시스템은 Gemma4가 응답했다고 생각하고 빈 문자열을 그대로 downstream에 전달

### 3.5 수정 내용

```python
async def _call_local(messages):
    """Gemma4 (llama-server) completions API — 수동 포맷"""
    # GGUF chat template 버그 우회
    prompt_parts = []
    for m in messages:
        role = m.get('role', 'user')
        content = m.get('content', '')
        if role == 'system':
            prompt_parts.append(f'<start_of_turn>system\n{content}<end_of_turn>')
        elif role == 'assistant':
            prompt_parts.append(f'<start_of_turn>model\n{content}<end_of_turn>')
        else:
            prompt_parts.append(f'<start_of_turn>user\n{content}<end_of_turn>')
    prompt_parts.append('<start_of_turn>model\n')
    prompt = '\n'.join(prompt_parts)

    response = await loop.run_in_executor(None, lambda: local_client.completions.create(
        model="local-model",
        prompt=prompt,
        temperature=0.7,
        max_tokens=3500,
        stop=['<end_of_turn>']
    ))
    text = response.choices[0].text.strip()
    return text, "Gemma4 (로컬)"
```

### 3.6 근본 해결 (향후)

`completions.create()` 우회는 임시 방편이다. 근본 해결 방안:

1. **GGUF 재변환**: 원본 Gemma4 checkpoint에서 chat template을 올바르게 설정하여 GGUF 재생성
2. **llama-server --jinja 0**: Jinja 템플릿 엔진 비활성화 (llama.cpp가 내장 fallback template 사용)
3. **--chat-template 명시**: llama-server 실행 시 올바른 Gemma4 chat template을 문자열로 전달
4. **모델 업데이트**: 최신 llama.cpp 버전에서 GGUF 호환성이 개선되었는지 확인

## 🔴 결함 #4: Telegram Markdown Parsing — 사용자 콘텐츠를 Markdown으로 전송

### 4.1 시스템 컨텍스트

```
사용자 → /read wiki/00_Meta/hot.md
  → hermes_file_ops.py cmd_read()
    → update.message.reply_text(파일내용)
      → Telegram Bot API → parse_mode 기본값 = "Markdown"
        → Telegram이 파일 내용을 Markdown으로 파싱 시도
          → "_", "*", "`", "[" 등의 특수문자가 파일 내용에 포함
            → "Can't parse entities" Telegram API 에러 발생
              → 메시지 전송 실패 (사용자에게 빈 응답)
```

### 4.2 증상 상세

1. **명령어**: `/read [파일경로]` — 파일 내용을 Telegram으로 전송
2. **에러 메시지**: Telegram Bot API가 `Bad request: Can't parse entities` 반환
3. **사용자 경험**: 파일 내용이 전송되지 않고 에러만 표시됨
4. **발생 조건**: 파일 내용에 Telegram Markdown 특수문자(`_`, `*`, `` ` ``, `[`, `]`, `(`, `)`, `~`, `>`, `#`, `+`, `-`, `=`, `|`, `{`, `}`, `.`, `!`)가 포함된 경우

### 4.3 재현

```python
# 📄 파일 내용 (예: hot.md)
"`src/` 디렉토리에서 **config.py** 파일..."
#   ^           ^^        ^^
#   백틱       별표      별표
#   → Telegram Markdown 파싱 오류
```

```
Python traceback:
telegram.error.BadRequest: Can't parse entities: 
  Unsupported start tag 'pre' at byte offset N
# 또는
  Can't parse entities: character '_' is reserved
```

### 4.4 근본 원인

```python
# Telegram python-telegram-bot v22.5
# update.message.reply_text()의 기본 동작:
reply_text(text, parse_mode='Markdown')  # ← 기본값이 Markdown!
```

`parse_mode`를 명시하지 않으면 Telegram Bot API는 **기본적으로 Markdown 모드**로 메시지를 파싱한다. 파일 내용은 Markdown 포맷팅 의도가 없는데도 Telegram이 강제로 파싱을 시도하여, 제대로 닫히지 않은 `*`, `_`, `` ` `` 등의 특수문자에서 파싱 에러가 발생한다.

**특히 위험한 패턴 (파일 내용에 자주 등장):**
- 경로명의 `_` (snake_case: `my_config.py`)
- 코드 예시의 `` ` `` (백틱: `` `src/` ``)
- 강조 표시의 `*` (마크다운 파일 자체의 `**bold**`)

### 4.5 수정 내용

**파일:** `~/Applications/Mjauto/Scripts/hermes_file_ops.py`

**Before:**
```python
await update.message.reply_text(f"📖 {target} 내용 (일부):\n\n{truncated}")
# parse_mode 없음 → 기본 Markdown → 파일 내용 파싱 실패
```

**After:**
```python
await update.message.reply_text(f"📖 {target} 내용 (일부):\n\n{truncated}", parse_mode=None)
# parse_mode=None → 평문 전송 → 파싱 에러 없음
```

동일 함수 내 두 `reply_text` 호출(235번째 줄 부분내용, 237번째 줄 전체내용) 모두 수정 완료.

### 4.6 보조 수정사항

- Header 문구의 `**볼드**` 제거 (parse_mode=None에서는 의미 없음)
  ```python
  # Before: f"📖 **{target}** 내용 (일부):\n\n{truncated}"
  # After:  f"📖 {target} 내용 (일부):\n\n{truncated}"
  ```

### 4.7 동일 패턴 탐지 결과 및 구조적 리스크

**동일 패턴 탐지 결과:**
Hermes1 봇 전체 코드베이스에서 `reply_text` 호출을 전수 조사한 결과, **사용자 콘텐츠(파일 내용)를 Markdown으로 전송하는 경로는 `/read`가 유일**했다. 나머지 `parse_mode="Markdown"` 사용처는 다음과 같이 안전:

| 위치 | 내용 | 안전 이유 |
|------|------|-----------|
| AI 응답 (`_reply_long(ans)`) | LLM이 생성한 markdown | LLM이 올바른 markdown 생성, AI 응답은 잘 형성됨 |
| 시스템 알림 | 코드 내 고정 문구 | Telegram 호환 markdown만 사용 |
| HELP_TEXT | 고정 도움말 | 수동 검증된 markdown |
| 칸반 명령어 | 고정 포맷 메시지 | Telegram 호환 markdown만 사용 |

**구조적 리스크 — `_reply_long()` chunk 경계 markdown 깨짐:**

`handlers/_base.py`의 `_reply_long()` 함수는 기본 `parse_mode='Markdown'`을 사용하며, 긴 텍스트를 3800자 단위로 분할 전송한다. 문자 단위 fallback 분할(367-368행)이 발생하면 chunk 경계에서 markdown 문법이 깨질 수 있다:

```
Chunk 1 (3800자): "```python\nprint('hello')\nprint(..." ← 코드블록 닫힘 없음
Chunk 2 (나머지):  "...')```\n" ← Can't parse entities!
```

**위험도:** 🟢 낮음 — `_split_text()`가 우선 개행 단위로 분할(안전)하며, 문자 단위 fallback은 텍스트에 3800자 연속 개행이 없을 때만 발생. 현재까지 실제 보고 없음.

**권장 조치:** chunk 경계에서 markdown이 깨지는 사례가 실제 발생하면, `_split_text()`에 markdown-safe splitter(열린 태그 감지 후 닫기)를 추가하거나 해당 호출에 `parse_mode=None`을 명시.

### 4.8 교훈

1. **Telegram `reply_text()`의 기본 `parse_mode='Markdown'`은 함정이다.** 파일 내용이나 사용자 입력을 전송할 때는 항상 `parse_mode=None`을 명시해야 한다.
2. **사용자 콘텐츠를 보내는 모든 경로**는 설계 단계에서 markdown 파싱 위험을 고려해야 한다. "파일 내용을 그대로 보여준다"는 요구사항은 반드시 `parse_mode=None`과 함께 구현되어야 한다.
3. **`_reply_long()`의 chunk 분할**은 markdown-safe하게 설계되지 않았다. LLM 응답은 일반적으로 안전하지만, 코드 덤프 등 markdown 구조가 긴 콘텐츠는 chunk 경계에서 깨질 가능성이 있다.

## ⚠️ 잠재적 구조적 리스크 (Potential Future Structural Risks)

이 시스템에서 현재 발견되지 않았지만, **패턴 유사성**으로 보아 발생 가능한 리스크:

### Risk 1: `hermes2_bot.py` 동일 Zombie Poller 패턴

**위험도:** 🔴 높음
**근거:** Hermes2도 PTB 또는 유사 polling 방식을 사용할 가능성이 높음 (`venu/hermes2_bot.py`). 코드를 확인하지 않았지만, 동일한 `app.run_polling()` 또는 `loop.run_forever()` 계열을 사용한다면 동일한 좀비 문제에 노출되어 있음.
**확인법:** `grep -n "run_polling\|run_forever" hermes2_bot.py`
**조치:** 확인 후 동일한 `updater.running` 모니터링 패턴 적용.

### Risk 2: `harness_agent.py` 추가 침묵 `except: pass`

**위험도:** 🟡 중간
**근거:** 793라인 중 2곳에서 발견됨. 추가 bare except 블록이 더 있을 가능성 높음.
**확인법:** `grep -rn "except.*:.*pass\|except:$\|except Exception:" --include="*.py" . | grep -v "noqa\|# intentionally\|__pycache__"`
**조치:** 전수조사 후 로깅 추가.

### Risk 3: Gemma4 GGUF 동일 문제 — 다른 모델 GGUF에도 존재 가능

**위험도:** 🟡 중간
**근거:** 동일한 변환 파이프라인(unsiloth → GGUF)으로 생성된 다른 모델 파일들도 동일한 chat template 문제를 가질 수 있음.
**확인법:** 각 GGUF 모델에 대해 `chat.completions` 요청 후 빈 문자열 반환 여부 확인.
**조치:** 모델별로 `_call_local`과 동일한 우회 적용 또는 GGUF 재변환.

### Risk 4: `MemoryConsolidator.start_background()` — Thread vs asyncio 간섭

**위험도:** 🔴 높음
**근거:** `hermes_local.py:529-531`에서 `MemoryConsolidator`가 `start_background()`로 별도 스레드에서 실행됨. 이 스레드가 asyncio event loop의 selector(kevent)와 간섭하거나, httpx 클라이언트(thread-safe하지 않음)를 공유할 경우 비결정적 충돌 발생 가능.
**확인법:** `MemoryConsolidator` 코드 검토 — httpx 또는 openai 클라이언트를 스레드 간에 공유하는지 확인.
**조치:** asyncio-safe한 별도 event loop에서 실행하거나, `run_in_executor`로 격리.

### Risk 5: `hybrid_router._call_primary_with_fallback` — 빈 문자열을 성공으로 처리

**위험도:** 🟡 중간
**근거:** `_call_local()`의 빈 문자열 반환 버그가 발견되기 전까지, `_call_primary_with_fallback`의 1차 시도는 `("", "Gemma4 (로컬)")`를 정상 반환으로 간주하고 fallback을 건너뜀. 모든 _call_* 함수가 정말 유효한 응답을 반환하는지 검증하지 않음.
**확인법:** `_call_primary_with_fallback`의 1차 시도 후 결과 검증 구문 확인.
**조치:** 반환값이 비어있거나 에러 형식이면 fallback으로 진행하는 validation layer 추가.

### Risk 6: launchd `KeepAlive=true` 무한 재시작 루프

**위험도:** 🟡 중간
**근거:** `com.hermes.bot.plist`에 `ThrottleInterval=5`를 추가했지만, 409 Conflict가 지속되는 환경(예: 동일 토큰을 사용하는 다른 프로세스 존재)에서는 5초마다 재시작 → Conflict → 재시작 무한 루프 가능.
**확인법:** launchd 로그 확인 (`sudo log show --predicate 'process == "launchd"' --last 1h | grep hermes`)
**조치:** 재시작 카운터를 파일에 기록하고, N회 연속 실패 시 plist 언로드 또는 알림 발송.

### Risk 7: `atexit` 핸들러 실행 실패로 인한 lock 파일 잠금

**위험도:** 🟢 낮음
**근거:** `hermes_local.py`에 `atexit.register(lambda fp=lock_fp: ...)`와 `atexit.register(_run_end_hook)`이 등록되어 있음. SIGKILL(강제 종료) 시 atexit 핸들러가 실행되지 않아 lock 파일이 잠긴 상태로 남을 수 있음. launchd 재시작 시 `fcntl.flock(LOCK_NB)`가 실패할 수 있음.
**확인법:** `flock` 실패 시 메시지 확인. `ensure_singleton()` 함수 검토.
**조치:** lock 파일 경로를 PID 파일과 결합하거나, SIGKILL에도 정리되는 방식(예: `/tmp/` 디렉토리 사용)으로 변경.

### Risk 8: `load_custom_env()`와 `os.environ` 공유 — 프로세스 간 env var 오염

**위험도:** 🟢 낮음
**근거:** `hermes_local.py`의 `load_custom_env()`가 `os.environ[k] = v`로 환경 변수를 설정함. 같은 머신에서 실행되는 다른 프로세스(예: Hermes2)는 영향을 받지 않지만, Hermes1의 자식 프로세스(예: subprocess)가 예상치 못한 env var를 상속받을 수 있음.
**확인법:** `os.environ`에 설정되는 모든 변수 목록과 subprocess 호출 지점 확인.
**조치:** subprocess 호출 시 `env=`로 필요한 변수만 명시적 전달.

  └── modules/dreaming_v2.py
        └── deep_distill()
              └── PEMS 게이트 통과 여부에 따른 offline_consolidation 호출 제어
```

### 5.2 증상 상세

1. **명령어 무응답**: 사용자가 `/memory` 명령어를 입력해도 봇이 무응답 상태에 빠짐.
2. **Dreaming 엔진 수렴 고착화**: `/memory_dream` 실행 시 항상 "수렴"으로 판정하여 실제 PEMS 점수와 무관하게 더 깊은 학습(또는 정화) 사이클이 차단됨.
3. **오프라인 병합 차단**: `delta_pems < threshold` 조건에 의해, PEMS 관문을 통과하는(수렴하지 않은) 정상적인 상황에서는 역설적으로 `offline_consolidation()`(지식 정화) 작업이 단 한 번도 실행되지 않는 논리적 모순 발생.

### 5.3 근본 원인

1. **`/memory` 명령어 누락**: `handlers/_memory.py` 파일 내에 `cmd_memory` 함수 자체가 정의되지 않았거나 연결되지 않아 라우터가 이 명령을 처리하지 못했다.
2. **PEMS 게이트 논리 오류**: `modules/dreaming_v2.py`의 `deep_distill()` 내부에서, `offline_consolidation()` 호출이 `delta_pems < self.pems_threshold` 일 때(즉, 성숙도가 수렴했다고 판단하여 LLM 연산을 조기 종료할 때)만 실행되도록 블록(`if`문) 내부에 배치되어 있었다. 정작 지식 패치가 생성되고 병합이 필요한 정상 통과 흐름에서는 이 작업이 생략되었다.

### 5.4 수정 내용

**파일 1:** `handlers/_memory.py`
- L1/L2/L3 메모리(Bio-Memory) 파일의 상태(크기, 항목 수, 최근 수정일)를 읽고 리포트하는 `cmd_memory` 함수를 완전하게 구현하여 추가.
- L2 `episodic_memory.json` 접근 전 자동 백업 기능(최근 5개 유지) 추가.
