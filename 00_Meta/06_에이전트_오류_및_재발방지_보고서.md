## [2026-07-04] BOT-003: mjstock_callback_bot.py 좀비 데몬 + getUpdates 충돌 경로 2건

**증상**: 전체 시스템 진단에서 "MJstock 토큰으로 이중 폴링 중"이라는 의심 발견 — `hermes_stock_bot.py`(com.hermes.stockbot)와 `mjstock_callback_bot.py`(com.mjstock.callbackbot) 둘 다 동일 텔레그램 봇 토큰을 사용 중이었음.

**근본 원인**:
1. **좀비 데몬**: `mjstock_callback_bot.py`는 과거(BUG-MJS-… 이전 세대) getUpdates 충돌을 겪은 뒤 154행에서 폴링을 코드로 이미 꺼둔 상태(`while True: time.sleep(3600)`, "게이트웨이가 수신 처리" 주석)였음. 그런데 launchd plist(`com.mjstock.callbackbot.plist`)의 `KeepAlive: true`가 이 빈 루프 프로세스를 계속 재생시켰음 — **기능이 다른 봇으로 이관됐어도 launchd job을 함께 정리하지 않으면 좀비 프로세스가 영구 존속**하는 패턴.
2. **잔존 충돌 경로**: `Mjstock/app.py:1667`의 "🔍 내 채팅 ID 자동 조회" 버튼이 동일 토큰으로 `getUpdates`를 직접 호출 — stockbot의 `run_polling()`(long-polling) 도중 사용자가 이 버튼을 누르면 409 Conflict + 콜백 유실 위험이 실제로 존재했음(실시간 폴링 충돌은 아니었지만, 잠재적 트리거였음).

**수정**:
1. `launchctl bootout gui/501/com.mjstock.callbackbot` — 좀비 프로세스(pid 7151) 종료
2. `~/Library/LaunchAgents/com.mjstock.callbackbot.plist` → `.plist.disabled` 개명(복구 가능한 형태로 비활성화)
3. `mjstock_callback_bot.py` 파일 자체 삭제(grep으로 무참조 확인 후) — 죽은 중복 코드
4. `app.py`의 getUpdates 버튼 → `.env` 읽기 전용 버튼("🆔 현재 저장된 채팅 ID 확인")으로 교체, 신규 조회는 `@userinfobot` 안내로 대체

**재발 방지**:
- 봇 기능을 다른 프로세스로 이관할 때는 **코드만 비활성화하지 말고 launchd plist도 함께 bootout + 개명** — `KeepAlive: true`는 "아무 일도 안 하는 프로세스"조차 영구 재생시킨다는 점을 반드시 인지
- 텔레그램 봇 토큰을 쓰는 모든 코드 경로(웹 UI 버튼 포함)에서 `getUpdates` 직접 호출은 활성 폴러가 있는 한 항상 금지 — `launchctl print` + `pgrep`으로만 진단, 실행 중인 폴러 확인 전 getUpdates 호출 자체를 봉인

**검증**: `test_mjstock_navigation.py` mock 회귀 전체 통과, 사용자 실클릭 확인("두 봇들 작동 잘됨"), `app.py` `ast.parse` 문법 검증 통과.

**연관 파일**: `Mjstock/mjstock_callback_bot.py`(삭제), `Mjstock/app.py`(수정), `~/Library/LaunchAgents/com.mjstock.callbackbot.plist`(비활성화), `Mjauto/Scripts/handlers/_stock_mjstock.py`(유일 콜백 처리자, 미변경)

**수정**:

### BUG-MJS-017: 버튼 표시 개수(N종) vs 실제 목록 개수 불일치

### BUG-MJS-018: 차트 조회 subprocess 동기 호출 → 콜백 타임아웃
**증상**: 버튼 눌러도 반응 없음, `telegram.error.BadRequest: Query is too old and response timeout expired`.

**수정**: 동일 스레드 분리 패턴 적용 — `asyncio.wait_for(loop.run_in_executor(...))`.

### BUG-COIN-001: 코인 "← 전체 검색기 결과로" 뒤로가기 시 버튼 소실("있다가 없다가")

### BUG-MJS-020 (자기귀책): 시간창 근사 매칭 → 무관한 검색기 섞임
**증상**: BUG-MJS-015를 "±30분 시간창" 근사 매칭으로 고쳤더니, 폭이 너무 넓어 무관한 검색기(우량주농사·초우량주·삼돌이US 등 6~18개)까지 뒤로가기 화면에 전부 섞여 나옴. 사용자 피드백: "듣도보도 못한 것들이 나타남".
**원인**: 시간 기반 근사 매칭 자체가 근본적으로 위험한 설계 — 실제 발송 시점에 어떤 검색기 집합을 보냈는지 정확히 알 방법이 없어 시간 근접성으로 추측한 것이 오판의 근원.
**수정**: 시간창 추측 방식 완전 폐기. 메시지 발송 시점에 정확히 어떤 검색기들을 보냈는지 `results/_batch/{batch_id}.json` 매니페스트 파일로 저장, 뒤로가기 클릭 시 이 파일을 읽어 정확히 그 집합만 복원. `screener/send_scan_result.py`/`auto_scan_morning.py`/`auto_scan_intraday.py` 3곳 모두 배치 매니페스트 저장 로직 추가. 콜백 데이터도 `mjstock_scan_list:{key}:{date_str}:{batch_id}` 형식으로 batch_id를 끝까지 실어 나르도록 `_handle_mjstock_scan_list`/`_handle_mjstock_chart`/`callback_mjstock` 디스패처 전부 수정.

### BUG-MJS-021 (자기귀책): batch_id 타임스탬프 형식 → 콜백 데이터 64바이트 초과
**증상**: 실제 프로덕션(auto_scan_morning.py, 2026-07-03 21:06~23:28 실행분)에서 "초우량(KR)" 버튼 클릭 시 무반응, `telegram.error.BadRequest: Button_data_invalid`.
**원인**: BUG-MJS-020 수정 시 batch_id를 `YYYYMMDD_HHMMSS`(15자) 전체 타임스탬프로 만들어 `mjstock_chart:{ticker}:{screener_key}:{date_str}:{batch_id}` 조합이 검색기 키가 긴 경우(`chowuryang_kr`, `nongsa_danta_kr` 등) 66바이트가 되어 텔레그램 콜백 데이터 64바이트 한도 초과.
**수정**: batch_id를 8자 hex로 축소.
```python
batch_id = format(int(datetime.now().timestamp() * 1000) & 0xFFFFFFFF, "08x")
```
최장 케이스(chowuryang_kr) 기준 59바이트로 안전권 확보.

**재발방지(6건 공통)**:
- 텔레그램 인라인 버튼 콜백 데이터는 항상 **64바이트 제한**을 염두에 두고 설계할 것 — 여러 식별자(screener_key+date_str+batch_id 등)를 이어붙일 때 최장 케이스 바이트 수를 검증 없이 늘리지 말 것
- 시간 기반 "근사 매칭"(±N분 창)으로 배치/그룹을 추측하는 설계는 위험 — 정확한 그룹 식별이 필요하면 명시적 매니페스트(파일/DB)로 저장해 참조할 것
- 여러 프로세스(수동 스크립트 vs 크론 자동스크립트 vs 텔레그램 봇 프로세스)가 협업하는 구조에서 코드 수정은 봇 프로세스 재시작(`launchctl kickstart -k gui/$(id -u)/com.hermes.stockbot`) 전까진 반영 안 됨 — 재시작 직후 Hermes 하네스 초기화(ActionRealization/FTS 인덱싱 등) 중 도착한 클릭은 "Query is too old"로 유실될 수 있어 재시작 후 몇 초 대기 후 테스트할 것
- 코드 수정 후 사용자에게 텔레그램 실클릭을 요청하기 전에, 먼저 핸들러 함수를 mock으로 직접 호출해 자동 검증할 것 — "고치고→사용자가 눌러서 확인→또 터짐"을 반복한 근본 원인은 사전 자동검증 습관 부재

**재발방지 도구(신규)**: `Mjauto/Scripts/test_mjstock_navigation.py` — 텔레그램 콜백 핸들러 함수를 FakeQuery mock으로 직접 호출해 실제 클릭 없이 왕복 경로(요약→목록→차트→뒤로가기)를 검증하는 자동 회귀 테스트. 검증 항목: ① 배치 매니페스트 정확 복원(무관한 검색기 미혼입) ② 뒤로가기 버튼의 batch_id 유지 ③ 종목 버튼 콜백의 batch_id 포함 ④ **모든 콜백 데이터 64바이트 이하**(BUG-MJS-021 재발 방지용) ⑤ KR 종목코드 앞자리 0 유지 ⑥ 에러/빈결과 화면에도 뒤로가기 버튼 존재. `_stock_mjstock.py` 수정 시 텔레그램 실클릭 요청 전 반드시 이 스크립트 선통과 필수.

**최종 검증**: 2026-07-04 새벽 — 사용자 텔레그램 실제 클릭 확인 완료("이제는 된다"). 프로덕션 auto_scan_morning.py도 새 batch manifest 코드로 25/25 검색기 정상 완료 확인.

## [2026-07-03] BUG-010: 나스닥500 아침 스캔 "스캔 실패" — cron ulimit(FD 256개) 고갈

**증상**: `MJstock 미국(나스닥500) 아침 스캔` 텔레그램 메시지에서 우량주농사·세력주농사·초우량주 3개 검색식이 `❌ 스캔 실패`로 표시. 로그(`logs/scan_morning.log`)에는 서로 다른 무관한 티커마다 "possibly delisted", "unable to open database file" 에러가 여러 날에 걸쳐 반복 등장 — 얼핏 개별 티커 문제처럼 보이나 실제로는 아님.

**원인**: cron으로 실행되는 프로세스는 macOS 기본 `ulimit -n 256`(launchd 기본값)을 그대로 상속. `run_scan.py`가 나스닥100(top-n 500) 전체를 순회하며 yfinance 실패 시 KIS API로 폴백하는데, 이 과정에서 실패한 HTTP 커넥션이 파일 디스크립터를 계속 점유 → 스캔 후반부(400번째 티커 이후)에 256개 한도 초과 → `save_scan_result()`의 `matched.to_csv()` 호출 시점에 `OSError: [Errno 24] Too many open files`로 전체 프로세스 크래시(rc=1). `run_scan.py` 내부 per-ticker 예외처리(`try/except: continue`)는 정상 동작하지만, FD 고갈은 그 예외처리 범위 밖(pandas to_csv, sqlite 연결 등)에서 터지므로 못 잡힘. 로그에 남는 "delisted"/"unable to open database file" 메시지들은 `result.stderr[:400]` 잘림 때문에 보이는 지엽적 증상이고, 실제 크래시 원인(traceback)은 이 400자 제한에 잘려 로그에 안 남음.
