# 🛡️ Git-기반 ACID 테스팅 하네스(Harness) 시스템 도입 분석 보고서

박사님께서 전달해주신 다운로드 파일 내의 `agent_harness.py`, `harness_config.py`, `hermes_local_patched.py` 구조를 면밀히 분석했습니다.

박사님의 우려대로, **제공된 패치 파일(`hermes_local_patched.py`)을 그대로 덮어쓰면 앞서 우리가 해결한 텔레그램 버튼 미작동 버그(Callback Query 버그)가 재발하며 시스템이 오작동하게 됩니다.** 따라서 코드를 통째로 바꾸는 것이 아니라, 구조를 철저히 검증하고 개선하여 안전하게 부분 적용해야 합니다.

---

## 📊 1. 이 시스템이 박사님께 정말 필요한가? (필요성 판단)

결론부터 말씀드리면, **"AI 에이전트가 내 코드를 스스로 수정하도록 허용할 것인가?"**에 따라 도입 여부가 갈립니다.

*   **도입해야 하는 경우 (필요성 매우 높음)**:
    박사님이 텔레그램을 통해 에이전트에게 "봇에 새로운 기능을 추가해줘" 또는 "에러난 스크립트 파일을 수정해줘"라고 지시하여 **AI가 스스로 코드를 수정하고 실시간으로 반영하게 하고 싶을 때**입니다. 이 장치가 없으면 AI가 한 글자만 틀려도 봇이 즉시 다운되어 터미널을 열고 수동으로 복구해야 합니다.
*   **도입하지 않아도 되는 경우 (오버스펙)**:
    AI 비서를 오직 "지식 정리(Obsidian), 메모리 백업, 인터넷 검색, 대화 및 일정 관리" 등의 **데이터 조작/요약 용도로만 사용하고, 코드 수정은 인간인 박사님이 직접 하실 때**입니다. 코드를 고치지 않는다면 Git 브랜치를 따고 검증을 돌리는 ACID 하네스 레이어는 불필요한 시스템 복잡도만 가중시킵니다.

> **💡 권장 방향**: 박사님은 향후 가족들에게 이 시스템을 공유하고 점진적으로 자동 진화하는 비서를 꿈꾸고 계시므로, **안전 장치로서 하네스를 도입하되 아래의 단점들을 완벽하게 보완하여 탑재**하는 것을 추천합니다.

## 🔴 2. 기존 하네스의 치명적 단점 및 개선/보완 방안

제공된 `agent_harness.py`와 패치 파일에는 프로덕션 환경에서 발생할 수 있는 몇 가지 심각한 맹점들이 있습니다. 이를 해결할 구체적인 보안책을 제시합니다.

### ⚠️ 단점 1: 동시 수정 시 Git 충돌 (Merge Conflict)
*   **현상**: 에이전트가 격리 브랜치(`agent/...`)에서 작업하는 동안 박사님이 메인 브랜치(`main`)에서 수동으로 코드를 고치면, 검증 통과 후 자동 병합(Merge)할 때 충돌이 발생해 봇이 멈추거나 수동 조작을 요구합니다.
*   **🛠️ 개선 방안 (세션 락 및 자동 롤백 알림)**:
    *   에이전트가 하네스 세션을 시작하면 텔레그램 봇의 하단 메뉴 버튼 전체를 **"Locked (에이전트 수정 중...)"** 상태로 전환하여 다른 명령이나 수동 수정이 겹치지 않게 물리적 락(Lock)을 겁니다.
    *   자동 병합 실패 시, 에이전트가 스스로 해결하려다 코드를 더 망가뜨리지 않도록 즉시 세션을 종료하고 박사님께 충돌 파일 목록을 텔레그램으로 전송하여 개입을 요청합니다.

### ⚠️ 단점 2: 임시 보관함(`git stash`) 누적 현상
*   **현상**: 에이전트가 DoD(검증)에 계속 실패할 때마다 `git add -A && git stash`를 수행합니다. 수십 번 실패하면 Mac Studio의 Git 저장소에 정체불명의 쓰레기 스태시(Stash)가 계속 쌓여 디렉토리가 지저분해집니다.
*   **🛠️ 개선 방안 (격리 브랜치 완전 삭제 및 Stash 미사용)**:
    *   에이전트가 격리 브랜치(`agent/...`)에서 작업하다 실패한 경우, 굳이 메인 브랜치에 스태시를 만들 필요가 없습니다. 
    *   어차피 독립된 브랜치에 코드가 있으므로, 메인 브랜치로 돌려놓을 때는 `git checkout main` 후 **실패한 격리 브랜치를 `git branch -D`로 날려버리는 방식**을 택하면 쓰레기 데이터가 전혀 남지 않고 디렉토리가 항상 깨끗하게 유지됩니다.

### ⚠️ 단점 3: 논리적 버그(Logic Flaw) 필터링 불가
*   **현상**: 현재 검증 방식은 `py_compile`을 통한 단순 문법 검사(Syntax Check)뿐입니다. 즉, 에이전트가 문법은 맞지만 실행하면 무한 루프에 빠지거나 봇을 즉시 먹통으로 만드는 "논리적 버그"를 짜 놓아도 하네스는 이를 통과시켜 메인에 합쳐버립니다.
*   **🛠️ 개선 방안 (드라이 런 / 스모크 테스트 레이어 추가)**:
    *   문법 검사 외에도, 수정된 `hermes_local.py`를 백그라운드에서 임시로 실행해 보는 **스모크 테스트(Smoke Test)**를 DoD에 추가합니다.
    *   예: `timeout 3s python3 hermes_local.py --dry-run`을 실행하여 초기 로딩 중에 Import Error나 초기화 실패(NameError 등)가 발생하는지 실시간으로 검증한 뒤 합치도록 검증 레이어를 고도화합니다.

## 💥 3. 단점 개선 없이 원본 적용 시 발생할 파급력 분석

만약 제공된 원본 파일들을 개선 없이 그대로 시스템에 적용하거나 덮어쓸 경우 예상되는 현실적인 피해 시나리오입니다:

1.  **텔레그램 버튼 무반응 장애 재발 (심각도: 상)**
    *   `hermes_local_patched.py`는 콜백 쿼리 시 `update.message`가 `None`이 되는 텔레그램 라이브러리 특성이 반영되지 않아, `dreaming`이나 `ingest` 버튼을 누르면 내부 보안 필터에서 사용자를 차단해 버려 하네스 작동 자체가 먹통이 됩니다.
2.  **Mac Studio 저장소 오염 및 Git 꼬임 (심각도: 중)**
    *   에이전트의 작업 실패가 반복될 때마다 `git stash list`가 기하급수적으로 늘어나, 나중에 박사님이 개발을 위해 수동으로 `git stash pop`을 하려 할 때 엉뚱한 에이전트의 쓰레기 코드가 복원되어 작업 소스코드가 유실될 위험이 있습니다.
3.  **자가 치유 불능 루프 발생 (심각도: 상)**
    *   에이전트가 문법은 맞으나 실행 즉시 크래시가 나는 런타임 오류(Runtime Error) 코드를 메인 브랜치에 머지해 버리면, 봇이 무한 재시작되거나 완전히 죽어버립니다. 이때는 하네스도 함께 가동이 중단되므로 직접 SSH로 접속해 Git 롤백 명령어를 타이핑해야만 봇이 살아납니다.
